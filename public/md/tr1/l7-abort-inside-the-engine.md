# Abort inside the engine: where the news goes and who frees the blocks

_Read the engines · lesson `tr1.l7` · review · about 60 minutes [estimated]_

Builds on kernelspace: `ks:T5.L7`, `ks:T2.L1`.

Knowledge components: `tr1.abort-path`.

A streamed answer is a promise to keep working, and the client can break it at any moment. A tab closes, a phone goes into a tunnel, a script gives up. From that moment every token the engine makes is paid for and thrown away, and the blocks of KV memory that the request holds are taken from requests that somebody still wants. An engine that cannot take a request back leaks capacity, so abort belongs to the lifecycle and not to its edge.

nano-vllm has no abort. Its package has no way to take a request back, so every request in it runs to its end. **the library's front end is the engine class** [measured] The other four engines each have a path for the news, and the four paths are the best test of the lifecycle in this module, because an abort crosses sockets, queues and threads, the mechanisms of the first lesson, and then has to win a race against the GPU.

This is a minimal version of a lesson that another course owns. The Data Plane specialization teaches the stream that survives: the disconnect at the HTTP or gRPC edge, `select!` safety, shutdown, hedging and retries, in its fifth lesson, `DP5`. That course has not shipped, so TR1 carries the part that happens inside the engine, in under an hour [estimated]. The story here starts when the engine's front end notices that the client has gone, and it ends when the blocks are back in the pool.

The next three stages are the engine core's, and they hold the idea of the lesson. The message arrives on the engine core's input thread, and the input thread does something that a request never gets. [These lines](https://github.com/vllm-project/vllm/blob/v0.33.0/vllm/v1/engine/core.py#L2032-L2040) put an abort on two queues.

```python
# vllm/v1/engine/core.py, lines 2032 to 2040 at v0.33.0
    if request_type == EngineCoreRequestType.ABORT:
        # Aborts are added to *both* queues, allows us to eagerly
        # process aborts while also ensuring ordering in the input
        # queue to avoid leaking requests. This is ok because
        # aborting in the scheduler is idempotent.
        self.aborts_queue.put_nowait(request)

# Push to input queue for core busy loop.
self.input_queue.put_nowait((request_type, request))
```

The copy on `aborts_queue` lets the engine process the abort eagerly, and the copy on `input_queue` keeps the order of the input queue, so that no request is leaked. The comment gives the reason that makes two copies safe: aborting in the scheduler is idempotent. **put on aborts_queue and on input_queue** [measured] What "at once" means is in [these lines](https://github.com/vllm-project/vllm/blob/v0.33.0/vllm/v1/engine/core.py#L790-L795), in the step that you read in the fifth lesson.

The engine core drains `aborts_queue` after the forward returns and before it updates the scheduler from the output. **aborts_queue** [measured] That is the whole reason for the queue of its own. An abort has to be seen between two steps and not wait behind them, and the engine core has one place between the forward and the update where it can look. ## The step in flight

The queue of its own exists because of a race. When the abort reaches the engine core, the GPU may be running a step that includes the request, and with async scheduling the engine may have planned the one after it. Whatever the engine does, it must end with no block leaked and no token sent to a client who has gone. The three engines that you have read that can abort give three different answers.

vLLM frees the request when it processes the abort, and makes sure that the step in flight cannot undo it. It processes the abort before the scheduler update, so that when `update_from_output` reads the step's output for the request, the request is already finished and the update skips it. Its own comment names the case: a request aborted while the model is executing it, which can happen with pipeline parallelism or with async scheduling. **the output of a finished request is dropped** [measured]

Mini-SGLang frees the request in the turn of its loop that handles the message. The scheduler asks the prefill manager and then the decode manager to take the request out, and if either had it, frees its table slot and its cache entry. **the scheduler takes the request out and frees it at once** [measured] **the table slot and the cache entry** [measured] A request that has not started has little to free: the prefill manager removes its pending entry and returns the chunked request that the entry holds, if there is one. **the pending entry goes, and what it held is returned** [measured]

SGLang does not free a running request at all. It marks the request to finish. The request runs one more forward pass, and the code that finishes any request cleans up its KV allocation, which the comment gives as the reason: the abort reuses all the existing code. **to_finish, one more forward** [measured] The price is one more step, and what it buys is one place that frees blocks. SGLang has two other methods for requests that have not started to run. A request in the waiting queue is popped straight out of it, and something is still sent back to the tokenizer manager to clean up its state. **a request that has not started is popped out of the queue** [measured] A request in the grammar queue still runs one prefill, cut down to one token to make it cheap. **a request in the grammar queue still runs one cheap prefill** [measured]

So the second prediction's answer is one. Each of the three designs pays where you can point at it. vLLM needs a rule that the update skips a finished request, Mini-SGLang needs its scheduler to free in the middle of its loop, and SGLang pays a forward pass.

## The same news, four ways

The news does not reach the scheduler the same way in each engine, and the differences are the path's stages.

Mini-SGLang notices late and sends the news the long way. The API server looks for a disconnect only when the next chunk is ready to send. **checked when the next chunk is about to be sent** [measured] When it finds one it raises `CancelledError`, and the handler for that exception starts `abort_user` as a task of its own. **a disconnect starts abort_user as a task** [measured] `abort_user` waits a tenth of a second, deletes the request's mailbox entries, and sends an `AbortMsg` through `send_one`, **wait, forget the mailbox, send an AbortMsg** [measured] which puts it on `send_tokenizer`. **the message goes on send_tokenizer** [measured] The tokenizer worker is one loop for tokenize, detokenize and abort messages, **one loop for tokenize, detokenize and abort messages** [measured] and it turns each `AbortMsg` into an `AbortBackendMsg` that goes to the scheduler. **the tokenizer turns it into an AbortBackendMsg** [measured] That is three process boundaries from the client to the scheduler [derived]: the client to the API server, the API server to the tokenizer, and the tokenizer to the scheduler.

"Inside vLLM" has no queue of its own for aborts. At the post's commit the engine core handles an ABORT request in the same dispatch as an ADD, so the abort reaches the busy loop on the same input queue as a new request, behind the requests before it. **the input queue** [measured] Each turn of that loop begins by polling the queue, and the poll handles every request that is waiting, so an abort that arrives during a step waits for the step to end and for the update to run. **the poll at the top of the turn handles it** [measured] The status it ends in is the pin's. **FINISHED_ABORTED, as in the pin** [measured] So one of the boxes of the post moved, and it moved in a way that is easy to miss: the pin's engine looks for aborts between the forward and the update, and the post's looks at the top of the next turn.

SGLang notices in two places. A task that runs after the response ends waits two seconds and then aborts each of the request's ids that still has a state, **a background task waits two seconds, then aborts** [measured] and a coroutine that waits for its request's event also wakes on a timeout to ask whether the client has gone. **the waiting coroutine polls for a disconnect** [measured] The tokenizer manager sends the scheduler one abort for each request. **one AbortReq for each request** [measured] The tokenizer manager shares the main process with the HTTP server, so the news crosses two process boundaries from the client to the scheduler [derived].

The count of process boundaries is the quickest way to tell the engines' paths apart, and the model computes it from the stages.

## An abort the engine starts

A client that leaves is not the only reason to abort a request. vLLM's engine core never sees text, so a stop string is found in the API server, in the output processor, whose comment says that its step turns each request's new token ids into text and performs the stop checks. **the output processor detokenizes and performs the stop checks** [measured] The output handler then sends the engine core an abort for each request that finished on a stop string, as its comment says. **the frontend aborts a request that hit a stop string** [measured] It is the same path with another cause, and it is the reason that the engine core has to survive an abort for a request that is already finished.

> **Cancelling a running database query.** A cancel for a running query comes in out of band, on another connection, and the backend acts on it at the next point where it can stop safely, then releases what the query held. An abort is that. It is a message that travels beside the request and not along it, it is acted on at a safe point, and the safe point decides what the cancelled work costs.
>
> Where it breaks: A database backend can look for a cancel in the middle of its own work. A GPU step cannot be cut short from the host, so an engine acts on an abort between two steps, and a step already launched still runs to its end.

> **A gone request can still be in a batch.** In every engine here the abort arrives while a step is in flight. A trace that shows the last forward pass of a request after its client has left is not a bug. Look for what skips it. It is the update that passes over a finished request, or the finishing code that runs one pass later.

## What to carry

- An abort is a message that travels beside the request, and it has to win a race against the step in flight. The engines differ in where they let it win.
- vLLM at the pin gives the abort a queue of its own, drains it between the forward and the update, and skips the finished request in the update. Mini-SGLang frees at once. SGLang marks the request to finish and pays one more forward pass.
- The pin is not the post. The post's engine looks for an abort at the top of the next turn, and the pin's looks before the update.
