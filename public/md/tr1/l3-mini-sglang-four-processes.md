# Mini-SGLang: one request through four processes

_Read the engines · lesson `tr1.l3` · review · about 40 minutes [estimated]_

Builds on kernelspace: `ks:T5.L10`, `ks:T2.L1`, `ks:T3.L6`.

Knowledge components: `tr1.sglang-lifecycle`.

nano-vllm had no front. A caller, a loop and a GPU shared one thread, and a request crossed nothing but the host-to-GPU boundary. Mini-SGLang is what the same engine looks like once it is a server. It has an API server that speaks HTTP, a tokenizer, a detokenizer, and a scheduler for each GPU, joined by ZeroMQ for control messages and by NCCL for the tensors the GPUs exchange. **API server, tokenizer, scheduler per GPU, detokenizer** [measured] **ZeroMQ for control, NCCL for tensors** [measured] It is the smallest honest example of the shape that vLLM and SGLang share, and kernelspace T5.L10 drew that shape from far away. Here you stand next to it.

The README calls the codebase about **5000 lines** [measured] of Python. The Python files under `python/minisgl` have 8,090 physical lines [measured] at `9a91cfa`, counted on 2026-11-05. The part you need for a request's path is much smaller: the scheduler package is 846 lines [measured] and the server package is 840 [measured]. Every link in this lesson is a permalink at that commit, and the lines were read from its tarball.

## Three processes or four

The documentation draws four kinds of process: an API server, a tokenizer worker, a detokenizer worker, and a scheduler worker for each GPU. Launch it with its defaults and you get three. The reason is one line of the server's arguments. `num_tokenizer` defaults to zero, and zero means that the tokenizer is shared with the detokenizer. **the tokenizer is shared with the detokenizer** [measured] The launcher starts one scheduler for each rank, a single process named `minisgl-detokenizer-0`, and as many tokenizer processes as `num_tokenizer` says. The API server is the process that launched the others. **a scheduler for each rank, one detokenizer, num_tokenizer tokenizers** [measured]

The "worker" that does both jobs is one function, [`tokenize_worker`](https://github.com/sgl-project/mini-sglang/blob/9a91cfafe754aa85daee49998176275667eb58f2/python/minisgl/tokenizer/server.py#L59-L70), in one loop. It receives whatever arrives, sorts it into detokenize messages, tokenize messages and abort messages, and handles each kind. **one loop for tokenize, detokenize and abort messages** [measured] Both kinds of message reach it on the same socket when the tokenizer is shared, and that is why one function needs three cases.

Why does the lifecycle model draw four? Because the path has the same shape either way. The request goes out to the tokenizer, on to the scheduler, back to the detokenizer and back to the API server, and each of those is a hop over a socket whether the two ends of a hop are one process or two. The model draws the tokenizer and the detokenizer as two places so that a single path serves both launches, and it counts the same number of boundaries that a sampled token crosses on the way out. Keep that in mind when you lay the path: the shape is the lesson, and the process count is a flag.

The sockets are `ipc://` endpoints under `/tmp`, suffixed with the pid of the launching process, so the processes talk over Unix-domain sockets on one machine and not over a network. **ipc:// sockets named by the launcher's pid** [measured] The messages are msgpack frames on ZeroMQ's push and pull sockets, **msgpack frames on PUSH and PULL sockets** [measured] with publish and subscribe for the one fan-out, which is rank zero to the other ranks. **a PUB socket and a SUB socket that subscribes to everything** [measured] [`ZmqAsyncPushQueue`](https://github.com/sgl-project/mini-sglang/blob/9a91cfafe754aa85daee49998176275667eb58f2/python/minisgl/utils/mp.py#L33-L47) is the same socket with an `await` on its send, for the API server's event loop. **the same push with an await** [measured]

Read the table's mechanisms down the page and the path has a rhythm. Six hand-offs between processes, which are HTTP in, four hops over ZeroMQ and the stream out. A queue where the request waits in the scheduler and a queue where the reply wakes its handler in the API server. A copy down, two launches, a copy up, and a sync that belongs to the next turn. Two of the hand-offs are quieter than the rest. The first is the API server's mailbox. Each request gets a uid, a list and an `asyncio.Event`, and a listener task reads every reply off the socket, appends it to its request's list and sets its event. The handler that is waiting on the event wakes and streams the chunk, and it waits with a bare `await` and no timeout. **a bare await on the event, with no timeout** [measured] That is a queue between two tasks of one event loop, and it is where `mini.ack-mailbox` sits. **an event and a list for each request** [measured] The second is the scheduler's own waiting list, `pending_list`, a plain Python list. The loop below reads the messages that add to it and schedules from it in one thread, so it is a queue between two steps of one thread and not between two threads.

## The scheduler's loop

The loop is where the overlap lives, and [`overlap_loop`](https://github.com/sgl-project/mini-sglang/blob/9a91cfafe754aa85daee49998176275667eb58f2/python/minisgl/scheduler/scheduler.py#L83-L106) is short enough to read whole.

```python
# python/minisgl/scheduler/scheduler.py, lines 83 to 106 at 9a91cfa
def overlap_loop(self, last_data: ForwardData | None) -> ForwardData | None:
    ...
    blocking = not (
        last_data is not None  # don't block if we have a batch to be processed
        or self.prefill_manager.runnable
        or self.decode_manager.runnable
    )
    for msg in self.receive_msg(blocking=blocking):
        self._process_one_msg(msg)

    forward_input = self._schedule_next_batch()
    ongoing_data = None
    if forward_input is not None:
        with self.engine_stream_ctx:  # run the batch in the engine's stream
            self.engine.stream.wait_stream(self.stream)
            ongoing_data = (forward_input, self._forward(forward_input))

    self._process_last_data(last_data)
    return ongoing_data
```

One turn does five things in this order. It reads messages from the socket, and blocks only if there is nothing else to do. It schedules a batch. It launches the batch on the engine's stream. It processes the previous turn's data, whose first act is the wait on that batch's copy event. And it hands this turn's data to the next one. **launch this batch, then process the last one** [measured] The queue between the copy and the sync, which you met as a stage in vLLM and SGLang, is here a single argument: `last_data` is a one-slot buffer that carries a launched batch across one turn of the loop. **copy_done.synchronize() in the next turn** [measured]

Overlap has a price, and the authors wrote it into a comment. A request that finishes in one batch may already have been scheduled into the next, because the next was launched before the first was read. The scheduler keeps a set of the requests it finished last turn so that it does not free a request twice. **a request can be freed twice** [measured] The switch that turns overlap off is an environment variable, and it is on by default. **on** [measured]

The scheduler's rule for what to run is the one you read in nano-vllm. It builds a prefill batch if a request is pending, and a decode batch only if none is. **a prefill batch, or else a decode batch** [measured] The prefill budget is a number of tokens for the whole batch, and a longer prompt is cut into chunks of that size. **8192 tokens** [measured] **the smaller of the budget left and the prompt left** [measured] A request that has only part of its prompt in a batch is a `ChunkedReq`, and result processing skips it, so the token sampled at the end of a partial chunk is thrown away. **a chunked request keeps no sampled token** [measured] Chunked prefill is on by default. **true** [measured]

The cache is a radix cache by default, and the match is made one token short of the prompt, so the last token is always computed. **radix** [measured] **input_ids[: input_len - 1]** [measured] The engine replays a CUDA graph when the batch can use one and runs eagerly otherwise. **a graph when the batch fits one, else eager** [measured] **true** [measured] The inputs of a step are built in pinned host memory and copied down without blocking, as they are in nano-vllm. **pinned host tensors, copied with non_blocking=True** [measured]

## Two ranks

With more than one GPU, each rank has its own scheduler process, and the schedulers must agree on what to run. Rank zero is the only one that talks to the tokenizer. It receives the messages, publishes each raw message to the other ranks on a ZeroMQ publish socket, and broadcasts how many messages there are over the CPU process group, so that every rank handles the same list in the same turn. **a ZMQ publish, and the count over the CPU group** [measured] Every rank then schedules, copies and launches, and the GPUs join their partial results with a collective inside the model. Only rank zero sends results on to the detokenizer. **only rank 0 replies** [measured]

So the second prediction has a short answer. The path gains the publish to the second rank, a hop over a socket, and the collective between the two GPUs. That is two stages [measured by the course's sim on 2026-11-05 at `905b782`]. The model follows the request through rank one's side of the pair, where the engine runs every rank in parallel, until the collective brings the result back to rank zero, which samples and replies.

## Back to the first prediction

A sampled token leaves the scheduler's process for the detokenizer's, leaves the detokenizer's for the API server's, and leaves the API server for the client. That is three process boundaries [derived], and the number is the same whether the tokenizer and the detokenizer are one process or two, because the hop from the scheduler to the shared process and the hop back from it are still two hops. Keep the number for the contrast with vLLM, where the engine core sends its tokens to the API server, which turns them into text, so the same trip crosses two boundaries. **a background process with a busy loop** [measured] **the output processor detokenizes and performs the stop checks** [measured]

> **A request id and a promise.** The API server's mailbox is the correlation id of a message-driven service. A request goes out with an id, the reply comes back on a different channel, and a map from the id to a waiting task joins the two. Here the map is ack_map and event_map, and the waiting task is an async handler that sleeps on an Event.
>
> Where it breaks: A service that works this way usually puts a deadline on the wait and a retry on the send. This handler waits on its Event with no deadline, and its check for a client that has gone runs only between chunks, so a request that produces nothing is never found to be abandoned.

> **The diagram is not the launch.** The documentation draws four processes and the default launch runs three. The diagram is still right about the path, and wrong about the process table you will see in ps. When you read an engine, read its launcher as well as its architecture page, and write down which flags change the number of processes.
