## The overlap loop

The loop is the reason to read SGLang, and the version at the pin is the one you met in Mini-SGLang, grown up. The overlap scheduler is on by default, and a flag turns it off. **on** [measured] Here is [the skeleton of `event_loop_overlap`](https://github.com/sgl-project/sglang/blob/v0.5.23/python/sglang/srt/managers/scheduler.py#L2061-L2131), with the lines that a request's path does not need left out.

Read the order. The loop receives requests, picks the next batch, launches it with `run_batch`, appends the batch and its result to `result_queue`, and only then processes the result of the previous batch. **launch batch N, then process batch N-1** [measured] **the previous batch is processed after the launch** [measured] The queue that Mini-SGLang carried in one argument, `last_data`, is here a real deque, and it is the `sglang.result-queue` stage of the path. **launch this batch, then process the last one** [measured] The wait is part of processing a result. The prefill processor and the decode processor both wait on the batch's `copy_done` event before they read the result. **the prefill result processor waits on the copy event** [measured] **the decode result processor waits on the copy event** [measured] So the sync of batch N sits in the turn that launches batch N plus one, and the model draws the queue between the copy and the sync.

There is one exception worth knowing, because it is a rule about when overlap is worth having. ## What the loop leans on

Overlap works only if the CPU can launch batch N plus one without having batch N's answer on the host. SGLang's trick is the most surprising thing in the engine: in the plain path, the next batch's input ids do not come from the host.

At the start of a forward pass the scheduler fills a prefill batch's input ids by a copy down from pinned CPU staging. It fills a decode batch's by a gather from the **FutureMap**, which holds the last iteration's sampled token. **a decode batch's input ids are gathered from the FutureMap** [measured] The FutureMap is a relay indexed by request-pool slot. A forward pass writes its results to it, and the next iteration reads them back. **a relay for values across iterations** [measured] After a forward pass without speculation the scheduler publishes the batch's new lengths to the map and clears the batch's input ids, because the next iteration's are relayed through it. **the next input ids come from the relay** [measured] The map's token buffer is one integer for each slot, allocated on the map's device and not in host memory, and the scheduler builds the map with its own device. **one 64-bit integer for each request-pool slot, on the map's device** [measured] **the scheduler builds the map with its own device** [measured]

Say that again, because it is the idea of the whole lesson. The next decode's input ids are gathered from a buffer on the device, so launching batch N plus one does not wait for batch N's tokens to reach the host [derived]. The copy up to the host, `sglang.d2h` in the path, brings the same tokens to the CPU for its own work, and the CPU does that work one turn late. The GPU feeds itself, and the CPU follows. vLLM's default runner has the same idea in another place: it prepares its inputs on the GPU with Triton kernels, so that a value the CPU does not know yet can still be derived there. **Triton kernels** [measured]

The price of following late is paid at a request's end. A stop by length is predictable without the token, so before it launches a decode SGLang drops the requests that a queued result is about to finish by length. **requests that a queued result finishes by length are dropped before the launch** [measured] A stop on a sampled token is not predictable, and the decode result processor has a branch for a request that is already finished, which a note in the code says only happens when overlap is on. **a finished request can reappear in a result** [measured] In effect, one more batch can be launched for a request that has already stopped, and its result is skipped.

The loop works with three streams. The model runner creates the forward stream. **the model runner creates the forward stream** [measured] The scheduler creates a stream of its own. **a stream of the scheduler's own** [measured] In `run_batch`, the forward stream first waits for that schedule stream, and then the forward pass is launched in it. **the forward stream waits for the schedule stream** [measured] The third stream does the readback. The docstring of the function that issues it says the readback goes on `copy_stream` so that it overlaps the next forward, and that the forward stream never waits for it. **a stream for the readback** [measured] The figure draws the loop on the host's lane, above the forward stream's lane on the GPU.

## A prefix hit and a request for two samples

A prefix hit is found while the batch is built, and it is the `sglang.prefix-hit` stage of the path. In the scheduler's loop over the waiting requests, each candidate's prefix is matched against the tree cache by `init_next_round_input`, before the batch adder is asked to take the request. **matched in the scheduler's loop over waiting requests** [measured] The match is capped one token short of the input, so the last token is always computed, and the comment gives the reason as the logprob computation. **at most one token less than the input** [measured] It is one rule in four spellings. nano-vllm never looks up a prompt's last block, **the last block is never looked up** [measured] vLLM defaults the longest hit to the prompt length less one, **prompt length less one** [measured] and Mini-SGLang matches all of the input ids but the last. **input_ids[: input_len - 1]** [measured]

The second prediction's answer is three. When a request asks for `n` greater than one, the tokenizer manager does not send it once. It first sends the shared prompt as a request of its own with `max_new_tokens` set to zero, to put its prefix in the cache, waits for it, and then sends the `n` sample requests. **a prefix request first** [measured] For two samples that is one warmup and two samples, which is three requests [derived]. The other engines you have read do it differently. vLLM wraps the request in a parent and sends a child for each sample, so two requests. **n child requests** [measured] Mini-SGLang accepts `n` and serves one sample. **n is accepted and not used** [measured] nano-vllm's sampling parameters have no `n` at all. **temperature, max_tokens, ignore_eos** [measured] Count the requests and you have a fact that no diagram of the shape shows.

## Two ranks

With more than one rank, each rank is a scheduler process. Rank zero's scheduler receives the requests from the tokenizer manager and broadcasts them to all the other ranks. **rank 0 receives, and broadcasts** [measured] The path gains two stages, `sglang.broadcast` to the second rank and `sglang.all-reduce` between the two GPUs, and nothing else changes.

## What to carry

- The overlap loop launches batch N plus one and then processes batch N. The queue between them is `result_queue`, and the wait is part of the result processor.
- A decode batch's input ids are gathered from the FutureMap on the device, so the launch does not wait for the host's copy. That copy feeds the CPU's own work, one turn late.
- vLLM and SGLang look alike and differ in the same few places: where the detokenizer runs, how many requests an `n` makes, and what holds the launched batch.
