Knowledge components: `tr0.decoder-forward`, `tr0.hidden-syncs`, `tr0.triton-program-model`.

The last lesson ended on kernels that an engine launches, and an engine launches them from its own model code, which you have not read yet. The third lesson read Qwen3 as Hugging Face writes it. This lesson reads the same model as Mini-SGLang, an inference engine, writes it, at its commit `9a91cfaf`.

## The same model, written by an engine

Mini-SGLang's file `models/qwen3.py` is **83 lines** [measured] long. It holds the decoder layer, the model and the wrapper around it, and it takes its attention and its MLP from a second file, `models/utils.py`. The attention is the class `RopeAttn` of that file, imported under the name `Qwen3Attn`, and the layer builds it with `has_qk_norm` set. **RopeAttn, from models/utils.py** [measured]

The layer runs the same four pieces as the third lesson's: the input norm, the attention, the post-attention norm and the MLP. One thing is different in how it runs them. Each norm takes the residual along and returns the new one, so the residual add is a part of the norm and no line of the layer. **norm, attention, norm, MLP** [measured]

The projections are where the third lesson counted work. The Hugging Face attention makes the query, the key and the value with three projections, `q_proj`, `k_proj` and `v_proj`. Commit to what Mini-SGLang's attention does with the same input.

> **Predict `tr0.l5.p1`.** The attention of the third lesson makes the query, the key and the value with three matrix multiplies (matmuls), one for each of q_proj, k_proj and v_proj. Mini-SGLang's Qwen3 attention, at its pinned commit, makes the same three tensors from the same input. How many matmuls does it use for them? A linear layer is one matmul.
>
> The learner commits to a number in `matmuls`, graded within a relative tolerance of `0` [estimated] before the reveal. Ask them to commit to an answer and say why before you discuss it.

## What the engine changes

Mini-SGLang's attention projects once. `RopeAttn` builds one merged projection for the query, the key and the value, `LinearQKVMerged`, where the Hugging Face model keeps three. **one merged projection** [measured] Its output width is the number of query heads plus two times the number of key and value heads, all times the head size, which is the three outputs side by side. **(heads + 2 * kv heads) * head size** [measured] For Qwen3-0.6B that is **4096** [derived] rows: the 2048 of the query and the 1024 of each of the other two, added up [derived].

A linear layer in Mini-SGLang is one call of `F.linear` on its weight, so the merged projection computes the query, the key and the value with one matrix multiply, where the Hugging Face layer makes three. **one F.linear** [measured] The MLP does the same with its pair: the gate and the up projection are merged into one, `gate_up_proj`, and the activation and the down projection follow. **one merged gate and up projection** [measured]

Side by side, for Qwen3-0.6B:

- **The attention's input** goes through `q_proj`, `k_proj` and `v_proj` in Hugging Face, with 2048, 1024 and 1024 output rows [derived]. In Mini-SGLang it goes through `qkv_proj`, with 4096 rows [derived].
- **The MLP's input** goes through `gate_proj` and `up_proj` in Hugging Face, and through `gate_up_proj` in Mini-SGLang.
- **The rotation and the norms of the query and the key** are among the attention's own pieces in Hugging Face. In Mini-SGLang they live in the attention layer that `RopeAttn` calls.

`RopeAttn.forward` projects once into `qkv`, hands it to that attention layer, which holds the rotary embedding and the norms of the query and the key, and then applies the output projection. **merged projection, attention, output projection** [measured]

A merged weight is one launch where three were. Whether that makes a step faster the course has not measured, and the file does not say why its authors chose it. The course has not run Mini-SGLang either, so it does not say that the two files give the same logits.

One more line of the layer is for the next module. The layer's forward is wrapped in an NVTX annotation named `Layer_{}` with the layer's id, and the attention and the MLP carry their own. An NVTX annotation names a span of code so that a profiler can draw it as a labelled range. **one NVTX range per layer** [measured]

The merged output has to be cut back into three tensors. Slicing one dimension of a contiguous tensor gives a view, as the first lesson showed. Check the strides of a new slice before you read on.

## Kernels an engine owns

The fourth lesson stepped seven of vLLM's kernels on a CPU. They belong to Model Runner V2 (MRV2), the runner that vLLM uses by default, and they live in five files. Each is read at vLLM's commit `4ba787ec`, and its path is under `vllm/v1/worker/gpu/`. A commit is a pin: the file is read as it stood then, and the engine may have changed since. The course's other pins are releases, and PyPI shows the day on which the first files of PyTorch `2.14.0`, Triton `3.8.0` and transformers `5.19.0` went up. **2026-09-02** [measured] **2026-08-28** [measured] **2026-10-06** [measured] vLLM's own Dockerfile and its tests use Python `3.12`, the version of the course's environments too. **3.12** [measured]

- `sample/gumbel.py`, 417 lines [measured]: a temperature kernel, a Gumbel sampling kernel and the hash functions that draw its noise.
- `buffer_utils.py`, 357 lines [measured]: the staged writes of `StagedWriteTensor`, which starts at line `135`, applied by one Triton kernel.
- `block_table.py`, 414 lines [measured]: two kernels, one that gathers block tables and one that computes slot mappings.
- `input_batch.py`, 759 lines [measured]: seven kernels that prepare and update a step's inputs.
- `spec_decode/rejection_sampler_utils.py`, 1,411 lines [measured]: the Triton kernels of the speculative rejection sampler, six of them launched.

The line counts and the contents are read at the pin. **417 lines** [measured] **357 lines** [measured] **135** [measured] **414 lines** [measured] **759 lines** [measured] **7 kernels** [measured] **1411 lines** [measured] **six launched kernels** [measured]

The five files hold 18 kernels between them: 2, 1, 2, 7 and 6 [derived]. By their names, none of them is an attention or a matrix multiply. They sample a token, write to the engine's buffers, map a token to its place in the KV cache, prepare a step's inputs and check a draft's tokens. They are the engine's own work on the batch around the model, which is why a reader of the engine meets them.

Each kernel starts by asking where it is. `tl.program_id(axis)` is which program this is along an axis of the grid, and `tl.num_programs(axis)` is how many programs were launched along it. **the number of programs along an axis** [measured] The lanes of a program come from `tl.arange(0, BLOCK)`. Triton's documentation words the rule for the range as a start that must be a power of two, and the code checks that the end minus the start is one, so it is `BLOCK` that must be a power of two. **a power of two** [measured] **end minus start is a power of two** [measured]

The grid is not in the kernel but in the launch. The temperature kernel's launch has two axes: one counts the tokens, and the other counts the blocks of `8192` lanes that the vocabulary needs. **(num_tokens, cdiv(vocab_size, 8192))** [measured] The kernel masks the lanes of the block past the vocabulary. **the block past the vocabulary is masked** [measured] The fourth lesson's arithmetic gives the launch for Qwen3-0.6B, whose vocabulary has **151936** [measured] entries. `triton.cdiv` of that over `8192` is 19 blocks for each token [derived]. They hold 155648 lanes, and 3712 of them are masked, all in the last block [derived]. In the last block, 4480 of the `8192` lanes hold an entry [derived]. The course has not run this kernel on a vocabulary this size, and the arithmetic says nothing of how long the launch takes.

Say which program covers an element of a launch like this before you read on.

## A Rust crate on the hot path

SGLang does not keep all of its hot path in Python. At its release `v0.5.23` it carries a Rust crate, `sglang-radix-tree`, and the file `python_bindings.rs` is its seam: the place where Python calls into the Rust. The seam is written with PyO3, the library that lets Rust code define a Python extension module. This lesson reads one example of it, and no more.

The module that the file defines is named `mem_cache`, and a Python `import` of it gets the Rust tree core. **mem_cache** [measured] A function adds the Rust classes to it: the tree core itself, `RustUnifiedTreeCoreBinding`, and the parameter and result classes that its calls take and return. **the tree core and its parameter and result types** [measured]

A call across the seam reads like a Rust function over structs. `match_prefix` takes a `MatchParamsBinding` and returns a `MatchResultBinding`, and it calls the Rust core's `match_prefix` inside a `py.detach` closure. **params in, a result object out** [measured] What `py.detach` does to Python's own thread is not read by this lesson [unverified].

A tensor crosses the seam as well. The file imports `Device`, `Kind` and `Tensor` from the `tch` crate, so that a method can take a torch tensor. **the tch crate's Tensor** [measured] `PyTensor` is the newtype that bridges a `tch::Tensor` and a Python `torch.Tensor` over raw `THPVariable` pointers, and the file says the code is inlined from `pyo3-tch`. **a newtype over THPVariable pointers** [measured] The second lesson's question, view or copy, applies here too, and the lines the course read do not answer it [unverified].

A panic in the Rust core does not take the Python process down. The binding catches it and raises a Python `RuntimeError` whose message begins "Rust TreeCore panicked", and the core stays unusable afterwards. **a Rust panic becomes a Python RuntimeError** [measured]

This is one seam of one engine. The course has not measured what the Rust tree saves the engine, and nothing here says that it saves any time.
