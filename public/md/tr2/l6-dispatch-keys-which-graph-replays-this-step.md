# Dispatch keys: which graph replays this step

_The step loop · lesson `tr2.l6` · review · about 78 minutes [estimated]_

Builds on kernelspace: `ks:T5.L7`, `ks:T5.L4`.

Knowledge components: `tr2.dispatch-keys`, `tr2.graph-modes`, `tr2.graph-memory`.

The fifth lesson left the engine with a rack of graphs, captured at start-up for some shapes. Each step now has to be matched with one of them, or with none, and the match is a lookup on a description of the batch: the dispatch key. This lesson reads the key in both of vLLM's runners, shows why the mode you ask for is not always the mode that runs, and then counts what the graphs cost, because every graph is memory that the KV cache does not get. It ends with the module's graded level, `close`.

## A key for each runner

MRV2, the default runner, dispatches on a frozen dataclass, `BatchExecutionDescriptor`, with seven fields. **7 fields** [measured]

| Field | What it says of the batch |
|---|---|
| `cg_mode` | which routine runs: `FULL`, `PIECEWISE` or `NONE` |
| `num_tokens` | the token count of the batch, padded to a captured size |
| `num_reqs` | the number of requests, or null for a piecewise graph |
| `uniform_token_count` | the query length that every request shares, or null |
| `max_query_len` | a bound on the longest query, or null |
| `num_active_loras` | the adapter case: how many distinct adapters the batch uses, rounded up to a captured case |
| `num_ubatches` | the microbatch count |

At capture time MRV2 builds a list of candidate descriptors for every token count and every captured adapter case. For each mode it takes the descriptors with the smallest captured token count at or above the batch's, the `FULL` ones before the `PIECEWISE` ones, and dispatch returns the first candidate that fits the batch. **FULL candidates first, then PIECEWISE** [measured] **first compatible descriptor** [measured] In a mode with full decode graphs it captures a `FULL` decode descriptor for each capture size, rounded up to a multiple of the decode query length, and skips the sizes that would need more requests than the rail allows. **one FULL decode descriptor per rounded capture size** [measured] For the mixed routine it captures one descriptor for each capture size, and a piecewise descriptor has no request count. **one mixed descriptor per capture size** [measured]

"Fits" has six conditions: the uniform token count unset or equal to the batch's, the query-length bound unset or large enough, the request count unset or large enough, a token count at least the batch's, and the adapter case and the microbatch count equal to the batch's. **six conditions** [measured] A batch is a uniform decode when every request has the same query length, and the runner reports that length only when no request is still prefilling, except that a prefill chunk of one new token counts as a decode. **num_tokens == max_query_len * num_reqs** [measured] While a request is prefilling, the runner passes the query-length bound as null, so a descriptor that bounds it cannot match. **None for a batch with a prefill** [measured]

MRV1, the legacy runner, keys on a `BatchDescriptor` with five fields, and `has_lora` is one of them. **5 fields** [measured] Its dispatcher looks for a `FULL` key with the exact request count, then for a `PIECEWISE` key with the request count relaxed, and otherwise runs eagerly. **FULL, then PIECEWISE, then NONE** [measured] The published design document shows a key of four fields, which matches neither runner, so the document is stale on the key and the code at the pin is the reference. **4 fields** [measured] SGLang has no descriptor at all: it pads a decode batch to a bucket of batch sizes, and the next lesson sets its lists beside vLLM's.

> **A cache key.** A cache is looked up by a key, a hit returns the stored object, and a miss goes the slow way to the origin. The descriptor is the key, a graph is the stored object, and NONE is the miss, so the step is launched kernel by kernel.
>
> Where it breaks: A cache fills on a miss, and a graph does not. All the graphs are captured at start-up, so a shape that was not captured stays a miss for as long as the server runs, and the cure is the list of sizes and not the traffic.

## The mode you ask for and the mode that runs

An attention backend declares how much it can replay. There are four levels, from `ALWAYS`, which supports mixed prefill and decode batches, through `UNIFORM_BATCH`, for batches whose requests share one query length, and `UNIFORM_SINGLE_TOKEN_DECODE`, for decodes of one token, down to `NEVER`. **ALWAYS, UNIFORM_BATCH, UNIFORM_SINGLE_TOKEN_DECODE, NEVER** [measured] The design document lists the backends it knows, and the level it gives each.

| Backend | The level in the design document |
|---|---|
| FlashAttention v3 | **ALWAYS** [measured] |
| Triton attention | **ALWAYS** [measured] |
| FlashAttention v2 | **UNIFORM_BATCH** [measured], though its comment says it is really `ALWAYS` and that the listing is a workaround so that it falls back to `FULL_AND_PIECEWISE` |
| FlashInfer | **UNIFORM_SINGLE_TOKEN_DECODE** [measured], or `UNIFORM_BATCH` when it uses TRTLLM attention on Blackwell |
| Mamba attention | **UNIFORM_SINGLE_TOKEN_DECODE** [measured] |
| Any backend not listed | **NEVER** [measured] |

A model with several kinds of attention takes the minimum of its backends' levels, and vLLM downgrades the mode to the best fit. **the minimum of the backends** [measured] The rules are three. A mode with full graphs for mixed batches needs `ALWAYS`, and on a backend below it the mode becomes `FULL_AND_PIECEWISE` if attention is split out of the compiled graph, and `FULL_DECODE_ONLY` if it is not. A backend with no graph support at all raises an error there. **FULL becomes FULL_AND_PIECEWISE or FULL_DECODE_ONLY** [measured] A mode with full decode graphs on a backend that supports none becomes `PIECEWISE`, or `NONE`. **FULL decode without backend support becomes PIECEWISE or NONE** [measured] And with speculative decoding, whose decode batches carry the drafts, a full decode graph needs `UNIFORM_BATCH`. **speculative decode needs UNIFORM_BATCH for a full graph** [measured] The design document's own summary is the rule to keep: vLLM downgrades a requested mode to the closest one that the backend supports. **a requested mode may be downgraded** [measured]

Here is what runs when each mode meets each level, from the course's port of the rules, with plain decode and with attention split out of the compiled graph, which is how the port runs. Read on 2026-11-08 at `b5fb81a`.

| You ask for | `ALWAYS` [measured] | `UNIFORM_BATCH` [measured] | `UNIFORM_SINGLE_TOKEN_DECODE` [measured] | `NEVER` [measured] |
|---|---|---|---|---|
| `NONE` | `NONE` | `NONE` | `NONE` | `NONE` |
| `PIECEWISE` | `PIECEWISE` | `PIECEWISE` | `PIECEWISE` | `PIECEWISE` |
| `FULL` | `FULL` | `FULL_AND_PIECEWISE` | `FULL_AND_PIECEWISE` | the engine refuses |
| `FULL_DECODE_ONLY` | `FULL_DECODE_ONLY` | `FULL_DECODE_ONLY` | `FULL_DECODE_ONLY` | `PIECEWISE` |
| `FULL_AND_PIECEWISE` | `FULL_AND_PIECEWISE` | `FULL_AND_PIECEWISE` | `FULL_AND_PIECEWISE` | `PIECEWISE` |

The cell that matters is the third row. You ask for `FULL`, the setting that sounds like the most, and on a FlashInfer setup you get `FULL_AND_PIECEWISE`, which is not the same configuration and has different memory. ## Adapters and the key

An adapter is part of the key. With `cudagraph_specialize_lora` on, which is the default, vLLM captures graphs with and without active adapters, at the cost of a longer start and slightly more memory. **true** [measured] A second switch, `specialize_active_lora`, is off by default, and when it is on, vLLM captures a graph for each count of active adapters, in powers of two up to `max_loras`. **false** [measured] By default the one adapter graph is therefore the one for the cap plus one. **max_loras + 1 by default** [measured] The count that a batch dispatches on is the number of distinct adapters among its requests, in both runners. **distinct adapters of the batch** [measured] **distinct adapters of the input batch** [measured]

On the rail above, a cap of 2 adapters [estimated] doubles the graphs, from 12 [measured] to 24 [measured] in `FULL_AND_PIECEWISE`, because every size is captured twice, once for no adapter and once for the adapter case. The model prices each graph alone, so it doubles their memory too. The guide says only slightly more memory, and the course has no capture to say how much more.

TR5a is where adapters live: vLLM keeps them in a fixed number of GPU slots, and a batch that needs more distinct adapters than there are slots waits. **lora_slots = max_loras** [measured] **distinct adapters at most max_loras** [measured] Here the same cap decides how many graphs the engine takes memory for.

The level that plays this section's rule is `keys`, "which adapter counts to capture within a memory budget". It is not open yet: it waits for the table of the pinned dispatchers' own answers, which the owner has to produce (Q-10). Until it opens, the table of cases above is your practice.

## What the graphs take from the KV cache

A graph holds memory. The engine may use a share of the card's memory, which is set by default at **0.92 share of card memory** [measured], and the weights, the activations, the graphs and the KV cache all come out of that share. MRV2 gained its own estimate of what the graphs will take in v0.29.0. **v0.29.0** [measured] It makes the estimate while the engine is still profiling, before the real KV cache is allocated, **profiled before the KV cache is allocated** [measured] and the memory the cache may take is the requested memory minus the profiled non-KV memory minus that estimate. **requested - non-KV - graph estimate** [measured] The estimate is applied by default. **true** [measured] The profile captures only the largest `FULL` graphs, records what each took, and extrapolates the difference to the rest, so the estimate is a sum over the graphs and every graph you capture costs something. **a memory delta per captured graph** [measured]

The course's model prices a graph at 8 MiB plus 16 KiB for each token of its size [estimated], which are round figures: no capture has been measured on a card. On the rail of 12 [estimated], in each mode, with the sizes above, the model gives these. Read on 2026-11-08 at `b5fb81a`.

## Everything on is not the answer

The module's graded level puts the whole lesson on one night. `close` draws a night from the seed: a burst of tickets, a rail, a token budget, a cost card, a host card, an attention backend with its support level, and a room for the routines. You choose the configuration from the cards before any run: whether the next call is written during the fire, where its ids come from, the runner, the graph mode and the sizes to drill. Then the night is served once. The house is found by the model. Of a small menu of configurations, it is the cheapest in graph memory whose night is within 1% [estimated] of the best, and the room is exactly what the house's graphs take, so a configuration whose graphs take more does not start.

On its practice seed, `16`, the night is the small model's, on a rail of 8 clips [measured] with a budget of 128 tokens [measured], and the room is 18.125 MiB [measured]. Everything off, which is the legacy runner, the next call written after the fire, the ids written by hand and no graph, loses 76% [measured] of its clock to dark stretches: 243,067 µs [measured] of 319,593 µs [measured]. The house is MRV2 with the next call written during the fire, the ids carried by the GPU, and `FULL` graphs at the sizes 8 and 128 [measured]. Its night takes 74,900 µs [measured] with no dark stretch, and its two graphs take 18.125 MiB [derived], the whole room.

Now turn everything on. vLLM's default sizes for that rail are 1, 2, 4, 8 and 16 [derived], and the engine refuses to start in each of the four modes that use graphs, because their graphs take more than the room [measured]. The default mode at the house's own two sizes is refused too [measured]. With async scheduling on and the ids still written by hand, the night is served and has 55 dependency violations [measured], and the graded level scores a night with one violation at zero.

## What to carry

- A graph is found by a key. In MRV2 it is a seven-field descriptor, and the first captured descriptor that fits the batch wins, `FULL` before `PIECEWISE`. A miss is `NONE`, which is the comb.
- The mode you ask for is not always the mode that runs: the attention backend's support level downgrades it, and the log says which. Check the mode before you read a result.
- Graphs are taken off the KV cache before it is sized, so every graph costs KV tokens, and "everything on" is not the answer.
