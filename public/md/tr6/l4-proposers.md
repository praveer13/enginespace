# Proposers: n-gram, suffix, draft model, EAGLE-3 and MTP, and what moved at v0.33.0

_Speculation and structure · lesson `tr6.l4` · review · about 35 minutes [estimated]_

Builds on kernelspace: `ks:T6.L6`, `ks:t6.self-drafting`.

Knowledge components: `tr6.proposer-families`.

The last three lessons were about the sampler, which is the same whatever drafted the tokens. This lesson is about the drafters. A **proposer** does one thing: from a request's context, it names `k` tokens. What it needs to do that decides what you must install, what traffic it pays on, and which runner it lands on in the pinned engines. kernelspace T6.L6 gave you the economics of MTP and EAGLE. This lesson names the proposers that vLLM v0.33.0 and SGLang v0.5.23 ship, reads two of them in the code, and ends on a fact that changes what a benchmark means: the runner a proposer lands on.

## What a proposer needs

vLLM's configuration names the speculative method, and at v0.33.0 the name is one of a fixed list. **ngram, draft_model, suffix, eagle, mtp and more** [measured] Five of them are what a team chooses between, and a sixth is the hook for writing your own.

| Method | Drafts from | What has to exist |
|---|---|---|
| `ngram` | the prompt, by matching n-grams in it and proposing the tokens that followed a match **matching n-grams in the prompt** [measured] | nothing beyond the engine |
| `suffix` | the prompt and earlier generations, by frequency counts, with an adaptive number of tokens **prompt and past generations, with frequency counts** [measured] | the Arctic Inference package **Arctic Inference** [measured] |
| `draft_model` | a separate model, running its own forward passes | a separate draft model **a separate draft model** [measured] |
| `eagle3` | a head that reads features of the target | a head trained for this target |
| `mtp` | the target's own multi-token prediction module **the target model includes multi-token prediction** [measured] | a target that includes native MTP, from a family vLLM supports **only families that support MTP in vLLM** [measured] |
| `custom_class` | your class's `propose` method **speculative_config.model is a module path** [measured] | a module path in `speculative_config.model` |

The `model` key of the configuration follows the same split. It names a draft model, an EAGLE head or an auxiliary model, and for `ngram`, `ngram_gpu`, `suffix` and `mtp` it can often be left out. **ngram, ngram_gpu, suffix, mtp** [measured]

None of this changes the sampler. An n-gram or suffix proposer names a token and no probability, so the sampler treats q as one-hot on it, which the second lesson worked through. By default a model-based draft is one-hot as well, because `draft_sample_method` defaults to `greedy`. **greedy** [measured] The proposers differ in cost and in how often they are right, not in what the output is.

## Which one fits

vLLM's guide gives two pieces of advice to hold against any proposer. Speculation pays under medium-to-low QPS, memory-bound workloads. **medium-to-low QPS, memory-bound** [measured] And the methods fall into two groups: the model-based ones, EAGLE, MTP, draft models and PARD, give the best latency reduction, and the simpler ones, n-gram and suffix, give modest speedups without adding work at peak traffic. **model-based methods gain more** [measured]

The choice is mostly made by what a team already has. A target trained with MTP has its proposer inside it. A head trained for the target is an EAGLE-3 proposer waiting for a config line. A smaller sibling of the same family is a draft model. With none of those, traffic that quotes its own prompt suits `ngram`, and agent loops that repeat their own earlier outputs suit `suffix`, if the package is installed. When more than one is on hand, the guide's first group gains more.

SGLang ranks by the same logic. Its guide names EAGLE-3, run with `--speculative-algorithm EAGLE3`, as its recommended choice for the best speed and quality, **EAGLE-3** [measured] and NGRAM, which is CUDA-only, as the choice when no extra model is available. **NGRAM, CUDA only** [measured] Its built-in algorithm names are a list of eight, and any name registered with `SpeculativeAlgorithm.register` joins it, **EAGLE, EAGLE3, NEXTN, STANDALONE, NGRAM, DFLASH, DSPARK, UNO** [measured] which is its counterpart to vLLM's module path.

> **A prefetcher with and without training.** Hardware prefetchers fall into two groups. A stride prefetcher needs no training. It watches the addresses so far, guesses the next one, and pays only when the access pattern repeats. A learned prefetcher is trained on traces and pays on patterns that a stride cannot see. The n-gram and suffix proposers are the first group, copying what the text has already said. An EAGLE head or an MTP module is the second, trained on the target's own features.
>
> Where it breaks: A wrong prefetch costs bandwidth and the program still reads the right data. A wrong draft costs verified positions and the sampler still returns the target's distribution, but a model-based proposer also has a price that a prefetcher has not, which is the weights and the forward passes of the model that drafts.

## EAGLE-3 and MTP, as reading

You will not build either of these here. A head has to be trained, and the lab's proposer is a prompt-lookup one. But you should be able to read them, and reading starts with what they take in.

EAGLE drafts by autoregression at the level of the target's features, the second-to-top layer, which its authors found more straightforward than autoregression on tokens. **autoregression at the second-to-top-layer feature level** [measured] EAGLE-3 gives up predicting features for predicting tokens directly, and fuses the features of several layers of the target in place of relying on the top one. **direct token prediction and multi-layer feature fusion** [measured] MTP comes from somewhere else. DeepSeek-V3 trains its multi-token prediction modules with the model, so that they predict the extra tokens one after another and keep the causal chain at each depth, **sequential modules that keep the causal chain** [measured] and the model can discard them at inference or repurpose them for speculative decoding. **the MTP modules can be repurposed for speculative decoding** [measured] SGLang puts it in its own terms: MTP is speculative decoding, and its example launches it with the EAGLE algorithm, so MTP runs through the EAGLE workers. **MTP as speculative decoding, launched with EAGLE** [measured]

What the three share, and what the pinned code shows, is an input that a draft model does not have: the target's own hidden states. Read it in four places.

1. `vllm/v1/spec_decode/eagle.py` is a short subclass whose only job is to build the base proposer with `pass_hidden_states_to_model=True`. **pass_hidden_states_to_model=True** [measured]
2. The base class, `vllm/v1/spec_decode/llm_base_proposer.py`, says what the flag does. It adds the stored hidden states to the draft model's inputs, next to the token ids and the positions. **model_kwargs["hidden_states"]** [measured] For `eagle3` it also assumes that the head takes auxiliary hidden states, unless the head's own config says it does not. **eagle3 heads use auxiliary hidden states by default** [measured]
3. `vllm/v1/spec_decode/draft_model.py` builds the same base class with the flag set to False. **pass_hidden_states_to_model=False** [measured] The difference between a head and a model, in this code, is whether the target's hidden states go in.
4. `vllm/config/speculative.py` holds the names, and two of them mislead. `use_eagle()` is true for `eagle`, `eagle3`, `mtp`, `dflash` and `dspark`, and a comment above it calls the name usually a stand-in for speculative decoding that uses the target's hidden states. **eagle, eagle3, mtp, dflash, dspark** [measured] So a search for eagle that finds MTP is working as written. And the long list of model-specific MTP names in the method type, `deepseek_mtp` and its kin, is now a list of deprecated aliases: the config logs a warning and replaces any of them with `mtp`. **model-specific MTP names are deprecated aliases of mtp** [measured]

Medusa and the MLP speculator are gone. They were removed in v0.33.0, so a guide that still lists them describes an older engine. **removed in v0.33.0** [measured]

## What moved at v0.33.0

A proposer lives inside a runner, and the runner moved. Model Runner V2, MRV2, became vLLM's default for all models in v0.29.0, released on 2026-09-09. **v0.29.0** [measured] At v0.33.0 the engine uses MRV2 unless the environment turns it off, Triton is missing, or the configuration uses a feature MRV2 does not support yet. In the last two cases it falls back to the legacy runner, MRV1, and logs one warning. **on, unless Triton or a feature blocks it** [measured] Five things send a configuration back, and three of them are about speculation: the methods `suffix` and `custom_class`, parallel drafting for anything but DFlash and DSpark, and draft models with their own vocabulary. **5 reasons** [measured] A custom proposer therefore runs on MRV1. **MRV1** [measured]

The runner decides one thing more. Async scheduling is on by default, **on** [measured] and on MRV1 it works with only some methods: the EAGLE family, n-gram on the GPU, a draft model, DSpark and DFlash. Asked for with another method, it raises an error. Left to its default, it turns itself off with one warning. **pipeline parallelism; some speculative methods** [measured] So the answer to the prediction is that a custom proposer runs on MRV1 with async scheduling off. The table lists more cases, each worked from these rules.

| Configuration | Runner | Async scheduling |
|---|---|---|
| `eagle3`, nothing else set | MRV2 | on |
| `ngram`, nothing else set | MRV2 | on |
| `suffix`, nothing else set | MRV1 | off, with one warning |
| `suffix`, async scheduling requested | the engine refuses to start | not applicable |
| `custom_class`, nothing else set | MRV1 | off, with one warning |
| `draft_model` with a vocabulary of its own | MRV1 | on |

This is why the module's lab compares like with like. A plain run on MRV2 with async scheduling on, set against a custom proposer on MRV1 with it off, differs in the runner and in the scheduling as well as in the proposer, and the speedup it reports folds all three together. The plain run uses the same runner and the same async setting as the speculative run, and the receipt records both.

> **A method name does not tell you the runner.** Two configurations that differ in method can differ in runner, and in whether async scheduling runs. A speedup measured across them folds all of that into one number. Record the runner and the async setting beside every speedup you report, and compare a speculative run only with a plain run on the same runner.

The hook and the fallback list are the facts on this page most likely to change before the next pin. The course re-reads `custom_class_proposer.py`, the fallback list and the proposer dispatch at every re-pin, and so should you before you trust the table above.

## What to carry

- A proposer needs something. The n-gram method needs the prompt, suffix decoding needs the prompt, earlier outputs and a package, a draft model needs a second model, an EAGLE-3 head needs training on the target's hidden states, and MTP needs a target that was trained with it.
- In the code, the difference between a head and a model is whether the target's hidden states go in. In a config check, `eagle` means that they do, and MTP is included.
- At the pin, `suffix` and `custom_class` run on MRV1, and on MRV1 async scheduling turns itself off for the methods outside a short list. Compare a speculative run only with a plain run on the same runner and the same async setting.
