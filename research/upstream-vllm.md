## 1. What changes in the course

1. **Pin v0.33, not v0.31 or v0.32.** v0.33.0 shipped on 2026-11-01 (GitHub) and 2026-11-02 (PyPI) [measured]. Minors arrive every 13.8 d (median of 8 intervals) [derived], not "every 2-3 weeks". No x.y.1 patch exists for 0.28 through 0.33 [measured]. v0.33.0 is the first minor with CUDA 13.0 wheels only, so a rented 4090 needs a host driver of R580 or newer; v0.32.0 is the fallback (R4, §3).
2. **MRV2 is the default runner, so TR2 teaches it as the base.** MRV2 became the default for all models in v0.29.0 (2026-09-09) [measured], which answers the question §10 leaves open ("when MRV2 became default on CUDA"). MRV1 is deprecated but still ships: `gpu_model_runner.py` is 7,192 lines at v0.33.0 [measured]. "Inside vLLM" reads MRV1-era code.
3. **`has_lora` is a dispatch key on the MRV1 path only.** The default runner (MRV2) dispatches on a 7-field `BatchExecutionDescriptor` that has `num_active_loras` and no `has_lora`. The design doc shows a 4-field NamedTuple that matches neither runner (G3-G5).
4. **Async scheduling has been the default since v0.14.0** (2026-01-20) [measured]. The reading target calls it "experimental" (M6, T2).
5. **The hybrid-KV doc is stale and adapters are slots, not pages.** Code handles N KV groups with a fixed-point lookup; the doc says "exactly two". vLLM keeps LoRA adapters in `max_loras` slots outside the KV pool, so "adapter pages in the same pool" is a design the learner builds, not an upstream mechanism (K1, K4).
6. **The KV connector contract is stable and has a reference implementation.** The method set is additive from v0.31.0 to `main`. A connector that does not subclass `SupportsHMA` turns the hybrid KV cache manager off, with only one log warning (K3, K6, K9).
7. **Speculation:** the standard rejection sampler is exact by design, and upstream's own test is a chi-squared check at about 10 sigma. Medusa and the MLP speculator were removed in v0.33.0. A custom proposer (`custom_class`) falls back to MRV1 at the pin (S3, S4).
8. **TR8 has exact upstream examples of its failure modes.** `--request-rate` defaults to `inf`, `--num-warmups` to 0, and percentiles to p99 only. `--max-concurrency` turns the run into a capped closed loop. Repeated runs against one server reuse the prefix cache (B1-B3).
9. **TR7's numbers need replacing.** The policy wording is verified. "Median PR cycle 1.04 d" has no source and does not reproduce: PRs merged 2026-10-19 to 2026-11-01 had a median created-to-merged time of 2.1 d overall, 0.85 d for org members and collaborators, and 4.2 d for everyone else (n = 1,005) [measured] (C5).
10. **The reading targets are stale in specific, listable ways.** "Inside vLLM" reads a commit that predates the pin by 449.6 d [derived], predates MRV2 and the CUDA-graph dispatcher, and names a file (`openai/api_server.py`) that is now a 59-line deprecated shim. nano-vllm's last commit is 190.8 d old [derived] (T1-T4).

## 3. Which minor to pin

**Recommendation: pin the v0.33 minor (tag `v0.33.0`, commit `4ba787ec9959e566d3b587a796dff07673324da5`), with `docs.vllm.ai/en/v0.33.0/` as the docs target.**

Why v0.33:

- It is the current release, and `stable` docs are built from it (R1, R5).
- Everything the modules need is verified at this tag (rows M-, G-, K-, S-, O-, P-, B-).
- A pin made now is about 6 or 7 minors behind by the first quarterly re-pin whichever minor is chosen, so one extra minor of age (v0.32) buys little (R2).
- The kernelspace lab twins can stay at v0.31.0: their scheduler facts still hold (M12).

Why not v0.31.0: it is two minors old, it still falls back to MRV1 for n-gram, and it keeps the three-architecture ROCm exception (M2, M3).
