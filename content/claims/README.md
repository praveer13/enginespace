## How the upstream claims were read

W1-T01 re-read every claim at its source on 2026-11-04. Where `research/upstream-vllm.md` and `research/upstream-sglang.md` (read on 2026-11-03) had the row, the claim starts from it, and the source was fetched again to quote it.

- **Where from.** A claim cites a file at the pinned tag or commit, with a `#L` anchor for the lines that hold its quote, or a release page, a pull request, a PyPI JSON page or the Inside vLLM post. It never cites `main`, `latest` or `stable`, because those move. A fact about an older release, such as the day a default changed, cites that release, and its TTL is 365 days. A fact that belongs to the pin has a TTL of 90 days, the quarter that the pin lasts.
- **How a quote was checked.** The tag's source tarball (checked against the tag's commit with `git get-tar-commit-id`) and each page were downloaded into their own folders and read as text, and never executed. Every quote was then found inside the lines its anchor names, with each run of whitespace read as one space. Two kinds of source cross a line break, and they are quoted differently.
  - **Prose that wraps** (a docstring, a comment, a page) breaks its lines at spaces, so a quote may cross the break. It writes the break as one space, drops no word at it, and has an anchor that names every line it touches. `vllm.spec.rejection-sampler.exact` joins lines 51 and 52 of `vllm/v1/sample/rejection_sampler.py` at v0.33.0, and `vllm.spec.bonus-token` lines 60 to 62 of the same file.
  - **A string that code splits across lines** (two literals in a row) has no space between its parts in its value, and the quotation marks of the literals come between them in the file. A quote of it is taken from one of its lines: `vllm.http.api-server-shim` quotes the first line of a deprecation message.

  `verify:claims` does not read sources, so only a re-read keeps this rule, and the only full one is the re-read at the next re-pin. `tests/content/tr1-sources.test.ts` and `tests/play/items-tr1-what-moved.test.ts` compare quotes with their anchored lines the same way, for the claims of `tr1.yaml` and `tr1-items.yaml`, wherever `ES_LIFECYCLE_SOURCES` names the unpacked trees (W1-T20, W1b-T03). The rule is written down because W1-T38's re-read of one claim from each of 23 claim files, on 2026-11-08, found the two quotes above joining a docstring's lines, which the old wording did not allow (`docs/waves/W1-report.md` §6).
- **How it was fetched.** Every request sent the User-Agent `Mozilla/5.0 (X11; Linux x86_64)`, with no cookie, no login and no other header that names anyone: `curl` sent `Host`, `User-Agent` and `Accept`, and `git ls-remote`, run with its configuration and credential helpers emptied, sent `Accept-Encoding`, `Pragma` and `Git-Protocol` as well. Pages and tarballs came from `github.com`, `codeload.github.com`, `raw.githubusercontent.com`, `pypi.org`, `vllm.ai`, `ui.perfetto.dev`, `developer.nvidia.com` and `docs.nvidia.com`, and the tags came from `git ls-remote`. No call used the GitHub API or the `gh` CLI.
- **A value is a number or a string.** A switch is written as the string `'true'` or `'false'`, and a list as one string.
- **An absence has no quote.** A claim that something is not there, such as an adapter in the KV block code, quotes the nearest line that shows the structure and says in its text where it looked.

## The hardware atlas

`hardware/` is what the physics floors of the receipt check read (W2-T09; ARCHITECTURE §8.5 rule 9, ASSESSMENT §6.4): for each GPU that a learner owns or rents, its memory capacity, its memory bandwidth and its peak rates by precision, as NVIDIA states them. A decode step cannot take less time than its bytes over the bandwidth, and no run can report a FLOP rate above the peak of its precision. It covers 14 GPUs in four files: `hopper.yaml` (`h100-sxm`, `h100-pcie`, `h200-sxm`), `ampere.yaml` (`a100-40-sxm`, `a100-40-pcie`, `a100-80-sxm`, `a100-80-pcie`), `ada.yaml` (`rtx4090`, `l4`, `l40s`) and `blackwell.yaml` (`rtx5090`, `rtx-pro-6000-server`, `rtx-pro-6000-workstation`, `rtx-pro-6000-max-q`). The H100 NVL, the H200 NVL and the B200 are not in it, and nor is a GPU of another maker. The header of each file lists the documents it was read from, with the size and the SHA-256 of each copy, so that a re-read can tell whether one changed.

**Ids.** `hw.<device>.<attribute>`, with a device key above. The attributes are:

| Attribute | What it is | Unit |
|---|---|---|
| `product-name` | the name that NVIDIA's Linux driver lists the GPU under | text |
| `mem-capacity` | the memory, with the vendor's "GB" kept as written | GB |
| `mem-bw` | the peak memory bandwidth, always in GB/s | GB/s |
| `mem-bw-tbps` | the same figure where the vendor writes TB/s (the H100 SXM and the H200 SXM), and their `mem-bw` is derived from it | TB/s |
| `fp32` | the peak of the CUDA cores, without the Tensor Cores | TFLOPS |
| `<precision>-dense` | the Tensor Core peak without sparsity, for `tf32`, `bf16`, `fp16`, `fp8`, `int8` and `fp4`, where the GPU has the precision | TFLOPS, and TOPS for `int8` |
| `<precision>-sparse` | the figure a vendor lists with sparsity where it lists no dense one (the H100 SXM, the H200 SXM and the L4), and the `-dense` claim of that precision is derived as half of it | as above |
| `fp16-fp32acc-dense`, `fp8-fp32acc-dense` | the RTX 4090 and the RTX 5090: the rate with FP32 accumulation, which is half of the `fp16` and `fp8` rate that accumulates in FP16. `bf16` is listed only with FP32 accumulation | TFLOPS |
| `<precision>-listed` | the RTX PRO 6000 Blackwell Server Edition only: a figure that its datasheet and page list without saying whether it counts sparsity | PFLOPS or TFLOPS, as listed |

A quote of a table row writes its cells in the order of the table, separated by " | ", and drops the footnote marks that a PDF glues to a label. A bandwidth that the vendor writes in TB/s is kept as written in a `mem-bw-tbps` claim, with the derived `mem-bw` in GB/s beside it. A `-listed` rate in PFLOPS is kept as listed, and a reader converts it (1 PFLOPS is 1,000 TFLOPS).

**Finding a GPU by its name.** A fingerprint records the name that NVML reports (ASSESSMENT §5.6). The check finds the device by comparing that string, exactly, with the value of each `product-name` claim. The device key is the second segment of the matching id, and the device's other claims follow from it. A name that no claim holds has no floors: the check says so and does not guess, since "NVIDIA H100 NVL" is not "NVIDIA H100 80GB HBM3". The strings are the product names in the Linux driver 580.196.07's list of supported GPUs, and the list of 620.70.06, the version that NVIDIA's `latest.txt` named on 2026-11-09 (220170 bytes, SHA-256 bcd9d80a06801003503298bdb8644e77f0240c3a7d828ee3c7616d860451dd0b), names the same GPUs the same way [measured 2026-11-09]. That nvidia-smi and NVML print these strings is not checked [unverified]; the owner's smoke runs (W2-T12) will show it for the GPUs they use.

**Dense and sparse.** NVIDIA's data-centre pages and datasheets list their Tensor Core peaks with sparsity and say so in a footnote, and the L4's datasheet adds that its "Specifications 1/2 lower without sparsity". For those GPUs the atlas keeps the listed figure as a `-sparse` claim and derives the `-dense` claim as half of it, which `verify:claims` recomputes. The architecture whitepapers print the dense figure beside the sparse one, and a `-dense` claim that comes from a whitepaper, or from a page that prints both, is the figure as printed. Where both are known the two agree closely, because the pages round their figures. The H100 SXM's derived dense peaks are within 0.05% of the whitepaper's [derived]: its TF32 is 494.5 here and 494.7 there. The L4's whitepaper prints whole numbers, and its FP8 and INT8 peaks, 242.5 here, are 0.2% above the 242 printed there [derived].

**What the numbers are, and where they are loose.** They are peaks, and a floor that divides by one inherits these limits.
- The whitepapers say "Peak rates are based on GPU Boost Clock", at the clock they list for the card. Whether a GeForce or an RTX PRO card can run above that clock is not stated in the documents read [unverified], so a ceiling on the FLOP rate of those cards needs a margin.
- The H100 PCIe's product brief lists 2,000 GB/s [measured 2026-11-09], and the Hopper whitepaper lists 2039 GB/s for the same card and marks it "Not Finalized for H100" [measured]. 5,120 bits at a 1,593 MHz DDR clock give 2,039 [derived]. The atlas takes the brief's figure, so a floor from it is about 2% stricter than the card's peak [derived]. For the H100 SXM the page's 3.35 TB/s and the whitepaper's 3352 GB/s agree to 0.1% [derived].
- The H200's datasheet and page mark every specification preliminary [measured 2026-11-09].
- The RTX PRO 6000 Blackwell Server Edition's datasheet and page print their Tensor Core figures with no word on sparsity, so the atlas holds them as `-listed` and not as `-dense`. As a ceiling a listed figure holds whichever way NVIDIA counted, and if it counts sparsity it is twice the dense peak [derived from the pairs the whitepaper prints for the Workstation Edition].
- Memory capacities keep the vendor's "GB". Whether it means 10^9 or 2^30 bytes is not stated in the documents read [unverified].

**Not in the atlas.** The links between GPUs and to the host (PCIe, NVLink), disks, power and clocks. docs/WORLD.md still lists the tier bandwidths of `packages/sim/tiers` as waiting for this atlas: they need a host-link claim for each GPU, and the documents read print a rate for only some (the L40S page gives PCIe Gen4 x16 as 64GB/s bidirectional, and the Hopper whitepaper gives PCIe Gen 5 as 128 GB/sec in total, where the GeForce whitepapers name the PCI Express generation and no rate), and they need a disk claim, which no GPU datasheet gives.

**At the next re-read.** Fetch the documents of each file's header again with the generic User-Agent, compare their SHA-256 with the header, and read the claims of any document that changed. A new driver list can add names. A new GPU adds a device key to one of the files, and its `product-name` claim is what makes the floors see it.

## What changed since kernelspace's twins

Kernelspace's two lab twins read vLLM v0.31.0 (claim `twin.vllm.scheduler`, lab 06) and SGLang v0.5.21 (claim `twin.sglang.treecore`, lab 07). enginespace pins vLLM v0.33.0, two minors later, and SGLang v0.5.23, also two minors later. Everything below was measured on 2026-11-04.

### vLLM, v0.31.0 to v0.33.0

- **The lab 06 twin still holds.** Each statement it reads from `vllm/config/scheduler.py`, `vllm/v1/core/sched/scheduler.py` and `vllm/v1/core/kv_cache_manager.py` is true at v0.33.0: `scheduler_reserve_full_isl` is on (`vllm.scheduler.reserve-full-isl`), chunked prefill is on (`vllm.scheduler.chunked-prefill-default`), `long_prefill_token_threshold` is 0 (`vllm.scheduler.long-prefill-threshold-default`), the policy is fcfs (`vllm.scheduler.policy-default`), the watermark is 0.0, `allocate_slots` takes `full_sequence_must_fit`, and under fcfs the victim is `self.running[-1]` (`vllm.scheduler.preemption-victim`). Only the line numbers moved: the victim line went from 771 to 938 [measured].
- **The files grew.** `scheduler.py` went from 3,359 lines to 3,783, with 608 lines added and 184 removed. `config/scheduler.py` changed by 8 lines added and 6 removed, `kv_cache_manager.py` by 24 added and 55 removed, and `request_queue.py` is identical [measured].
- **MRV2 can run more of what the twin's world had.** MRV2 fell back to MRV1 for 8 reasons at v0.31.0 and does for 5 at v0.33.0 (`vllm.mrv2.fallback-reasons`). The n-gram methods, `medusa` and `mlp_speculator`, stock `torch.compile`, sequence parallelism, elastic expert parallelism and Mamba cache mode `all` left the list, and heterogeneous-vocabulary draft models joined it [measured]. Of the speculative methods only `suffix` and `custom_class` still force MRV1 (`vllm.spec.custom-class-mrv1`).
- **Speculation lost two methods.** Medusa and the MLP speculator were removed in v0.33.0 (`vllm.spec.medusa-removed`).
- **The wheels changed.** From v0.33.0 the wheels and images are CUDA 13.0 only, which needs a host driver of R580 or newer. Earlier releases also published CUDA 12.9 wheels and images, and v0.32.0 was the last (`vllm.release.cuda-13-only`, `vllm.release.driver-r580`).
- **Structured output** has one deprecation: the LM Format Enforcer backend is opt-in in v0.34.0 and removed in v0.35.0 (`vllm.mask.lmfe-deprecated`).

### SGLang, v0.5.21 to v0.5.23

- **The lab 07 twin may not hold, and nobody has re-read it.** Four of the five Rust files that the twin names changed between the two releases: `unified_tree_core.rs` went from 5,666 lines to 6,203 (906 added, 369 removed), `node.rs` changed by 59 lines added and 14 removed, `components/full.rs` by 68 and 29, and `components/mod.rs` by 60 and 8. `unified_lru_list.rs` is identical [measured]. Every function that the twin names is still there (`match_prefix`, `match_prefix_helper_`, `split_node_`, `insert`, `insert_walk_step_`, `insert_commit_step_`, `evict_device_next_node` and `is_evictable_device_leaf_`), and the four crate tests that its answers cite are still in `src/tests/unified_tree_core.rs` [measured]. Whether each of the twin's three answers still holds at v0.5.23 was not worked out again [unverified]. A task that quotes lab 07's twin as SGLang's behaviour should do that first.
- **Removals.** v0.5.22 removed the `tc_piecewise` prefill graph backend (`sglang.cudagraph.tc-piecewise-removed`) and the `ChunkCache` class. v0.5.21 had already removed the legacy radix classes and `SGLANG_ENABLE_SPEC_V2` (`sglang.radix.legacy-classes-removed`, `sglang.spec.v2-only`), so the twin's release already sits on `UnifiedRadixCache`.
- **Additions.** v0.5.23 added `--goodput` to `bench_serving` (`sglang.bench.goodput-since`) and published opaque LoRA block ids and adapter names in its KV events (pull request 42817; `sglang.kv-events.lora-ids-since`, `sglang.kv-events.adapter-field`).
- **The pins differ in their libraries.** SGLang 0.5.23 pins `torch==2.14.1` and `xgrammar==0.2.7`, where vLLM 0.33.0 pins `torch==2.14.0` and `xgrammar==0.2.8` (`sglang.release.torch-pin`, `vllm.release.torch-pin`), so each engine gets its own environment (ARCHITECTURE §9.2). Mini-SGLang pins `torch<2.10.0` and needs a third (`mini-sglang.torch-pin`).

## At the next re-pin

Read each claim again at the new tag. A claim whose quote moved or changed raises a change card, and the research files' drift detectors (`research/upstream-vllm.md` §6) list the greps to start from. Change the `pin` entry in `course.lock.json` last, and bump `checkedAt` on the entries that were re-read.
