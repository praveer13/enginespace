The notional machine behind Service's practice run and TR2: `packages/sim/steploop`, at version v1. It was built as the TR2 spike (W0-T13, D-040), and W1-T12 added the graph modes and dispatch keys, the runner presets, the per-GPU engine defaults, the structured-output mask, the speculative step and the host term on the CPU lane. It runs one engine core's busy loop in integer µs on two lanes, `cpu-main` (the engine core's thread) and `gpu-stream` (the default CUDA stream). It takes a seeded workload and a configuration, and returns the lanes, a record per step and per request, and any violations. Its rules follow vLLM v0.33.0, the course's pin. The real engine is authoritative: when it disagrees with this card, the card is wrong.

## Models

1. **One step.** On `cpu-main` the step runs `schedule`, then `prepare` and `launch`. On `gpu-stream` its `forward` starts when the launch has ended and the stream is free. Back on `cpu-main`, `sync` returns the sampled ids to the host once the forward has ended, and `sample` updates the requests from them and checks for stops. vLLM's `EngineCore.step` makes the same calls in the same order. {{claim:vllm.step.order}}
2. **The scheduler.** One token budget per step, handed out to every request so that each catches up with the tokens it should have, and a cap on running requests. Running requests come first, one token each, and waiting requests follow in arrival order, which is vLLM's default policy. Chunked prefill is on, as it is by default in vLLM, so a prompt is cut into chunks to fit the budget. With it off, a prompt is admitted whole or not at all. The model emits a request's first token in the step that completes its prompt. Static batching, which the front page's first lane runs, forms a batch and admits nothing while any request of it is live in the engine's view (GAMES.md §3.1, D-043). {{claim:vllm.scheduler.no-phases}} {{claim:vllm.scheduler.order}} {{claim:vllm.scheduler.policy-default}} {{claim:vllm.scheduler.chunked-prefill-default}}
3. **Where a request ends.** A request's output length is the truth about it, and the scheduler never reads it. The request stops on EOS, and the engine learns of it only when the step that carries its last token is read back. On the front page the visitor hangs requests by hand, and a request's length is settled when it is hung: the k-th request hung gets the k-th length of the seed's workload, whatever its number, so the order the visitor taps in cannot change a run (GAMES.md §3, WORLD §2.2). {{claim:vllm.scheduler.stop-check}}
4. **Async scheduling off** is strictly serial (WORLD §2.6): the next step's `schedule` starts only after this step's `sample`.
5. **Async scheduling on** is the default in vLLM, and has been since v0.14.0. Up to two steps are in flight, as the engine's batch queue allows at one pipeline stage. The next step is scheduled, prepared and launched before the oldest step's result is waited for, so that CPU work overlaps the forward in flight. A request that stops on EOS still rides the next step, because the engine has not read the stop yet, and that step's token for it is thrown away: a ghost token (WORLD §2.6). {{claim:vllm.async-scheduling.default}} {{claim:vllm.async-scheduling.since}} {{claim:vllm.step.max-concurrent-batches.mrv2}} {{claim:vllm.mrv2.async-first}}
6. **The dependency check** (A§5.3). With async scheduling the previous step is still in flight when the next one is prepared. If the input ids are written on the device, as MRV2's GPU-side input preparation does, the stream's order makes each token ready before the forward reads it. If the CPU writes them from the host, it reads tokens that are not sampled yet, and the step raises a violation. Graded levels count violations (ASSESSMENT §4.3). {{claim:vllm.mrv2.gpu-input-prep}}
7. **The five graph modes.** vLLM has `NONE`, `PIECEWISE`, `FULL`, `FULL_DECODE_ONLY` and `FULL_AND_PIECEWISE`. The last two are pairs of routines, one for batches that only decode and one for the rest: `FULL_DECODE_ONLY` runs full graphs for the first and nothing for the second, and `FULL_AND_PIECEWISE`, the default at the pin, runs full graphs for the first and piecewise graphs for the second. A piecewise graph leaves the attention of each layer outside the graph, so a piecewise step replays one graph for each of the layers plus one, and launches attention once for each layer, which is [estimated]. A requested mode meets the support level of the attention backend and is downgraded to the nearest mode the backend can run, by the rules of `resolveGraphMode`. The modes are data (`GRAPH_MODES`), so a level can ask a learner which routine a batch will take (WORLD §2.5, GAMES.md §3.2). {{claim:vllm.cudagraph.modes}} {{claim:vllm.cudagraph.mode-routines}} {{claim:vllm.cudagraph.default-mode}} {{claim:vllm.cudagraph.piecewise-partitions}} {{claim:vllm.cudagraph.mode-downgrade}}
8. **Capture sizes and padding.** Unless the user lists sizes, vLLM captures a default list. {{claim:vllm.cudagraph.capture-sizes}} Its largest size is capped by default at {{claim:vllm.cudagraph.max-capture-size}}, or at {{claim:vllm.cudagraph.max-capture-size-blackwell}} on data-centre Blackwell, and is also set by `max_num_seqs` and the decode query length, and cut to the token budget (`vllmCaptureSizes`). A step is padded up to the smallest captured size that holds it. The padded tokens are computed and wasted: the GPU lane prices the padded batch, and the host lane prices the real one. Above the largest captured size, or with graphs off, the step launches one kernel at a time: kernels per layer, times layers, times the launch cost. A full graph costs one replay to launch. {{claim:vllm.cudagraph.padding}} {{claim:vllm.cudagraph.default-max-formula}} {{claim:vllm.cudagraph.sizes-budget-clamp}}
9. **The dispatch keys.** Which graph a step replays is decided by the runner's dispatcher, ported from the pinned source and kept as data. MRV2, the default runner, keys a graph by a `BatchExecutionDescriptor` of seven fields and splits batches by whether every row has the same token count. MRV1, the legacy runner, keys it by a `BatchDescriptor` of five fields, with a `has_lora` flag, and calls a batch a uniform decode when its longest query is the decode query length. Each tries a full graph first, then a piecewise one, then none. The design document's four-field key is stale at the pin and is modelled by neither. {{claim:vllm.cudagraph.mrv2-key}} {{claim:vllm.cudagraph.mrv2-dispatch}} {{claim:vllm.cudagraph.mrv1-key}} {{claim:vllm.cudagraph.mrv1-dispatch}} {{claim:vllm.cudagraph.design-doc-key}}
10. **Adapters.** A waiting request whose adapter would make one more than the cap on adapters is skipped, and the next waiting request is tried. Both runners dispatch on the number of distinct adapters among the rows of the step. With `cudagraph_specialize_lora` the engine captures graphs with adapters and graphs without, and with active-adapter specialisation it captures counts that grow by powers of two up to the cap, so a batch is rounded up to a captured count. A step with an adapter costs the GPU what the same step without one costs: the model prices no adapter kernels. {{claim:vllm.lora.admission-cap}} {{claim:vllm.cudagraph.mrv2-active-loras}} {{claim:vllm.cudagraph.mrv1-active-loras}} {{claim:vllm.cudagraph.mrv1-batch-trim}} {{claim:vllm.cudagraph.lora-specialize}} {{claim:vllm.cudagraph.lora-count-specialize}}
11. **Graph memory.** Every captured graph holds memory that the KV cache does not get. Since v0.29.0 the engine estimates what the graphs will take before it sizes the cache, and subtracts the estimate from the budget, so that a prediction of KV capacity that ignores the graphs is too high by their sum. The model prices a graph as a fixed part plus a part for each token of its size, both [estimated], and `kvBudget` subtracts the sum from the requested memory, which is the card's memory times `gpu_memory_utilization`. This is a calculation beside the loop and not a limit in it (see Ignores). {{claim:vllm.cudagraph.memory-before-kv}} {{claim:vllm.cudagraph.memory-subtracted}} {{claim:vllm.cudagraph.memory-profile-extrapolates}} {{claim:vllm.cache.gpu-memory-utilization-default}}
12. **The runner presets** (D-041). `mrv2` is the default runner, and `v1` the legacy one that still ships. A preset sets the host card, the dispatch key above, and what speculation does: MRV2 hands the methods it does not take back to MRV1, and MRV1 runs async scheduling with only some methods. A configuration that vLLM would refuse is refused with the reason. {{claim:vllm.mrv2.default-rule}} {{claim:vllm.mrv2.fallback-reasons}} {{claim:vllm.async-scheduling.mrv1-limits}}
13. **Per-GPU engine defaults.** The engine's defaults depend on the card's memory, so the model holds a row for the `RTX 4090` and one for the `H100` (WORLD §2.10, GAMES.md §3.2). vLLM sets the token budget and the cap on sequences by the card's memory tier, for the server and for the offline class. SGLang sets its chunk size and the largest batch it captures a decode graph for by the card's memory, and generates its bucket lists from them. The SGLang rows are data for the course's comparisons and do not drive this loop. {{claim:vllm.batch-defaults.threshold.large-gib}} {{claim:vllm.batch-defaults.small.server-tokens}} {{claim:vllm.batch-defaults.large.server-tokens}} {{claim:sglang.cudagraph.decode-max-bs.small}} {{claim:sglang.sched.chunked-prefill-size.small}}
14. **The structured-output mask** (WORLD §2.8). Each row that samples a structured request needs a row of the bitmask, and filling a row costs the host card's `maskPerSeqUs`. The engine thread builds the mask after the forward has been launched without blocking, so with overlap the fill runs while the GPU works, and without it the fill sits between the sync and the sample. Under async scheduling a row whose input token is still in flight cannot be filled until the step before has been read back, whatever the overlap switch says, because that step waits for the previous step's tokens before it can sample. Above a threshold of structured requests, and only without speculative tokens, the fill is cut into tasks for a pool of threads, and the engine thread waits for them all. With speculation every request owns a block of rows, one for each position that may be sampled. {{claim:vllm.mask.overlap}} {{claim:vllm.mask.deferred-sampling}} {{claim:vllm.mask.fill-parallel-threshold}} {{claim:vllm.mask.fill-rows-per-request}}
15. **The speculative step** (WORLD §2.7, A§5.5). A running request in decode carries its drafts, `1 + k` tokens, cut to what is left of the step's token budget, so the step is a uniform decode of `1 + k` tokens a row and the dispatcher sees that query length. Each draft is accepted with probability α until the first that is not, and the round emits the accepted drafts and one more token of the target's own, so it emits `1 + A` tokens for `A` accepted. On average a round emits `1 + α + … + α^k` tokens, and the model draws the accepted prefix from the request's own seeded stream. The drafts run inside the step's forward and cost the GPU lane a share of a plain decode step of the same rows for each draft, which is [estimated]. The exact accept-and-recover rule is W1-T26's. {{claim:vllm.scheduler.spec-drafts}} {{claim:spec.paper.expected-tokens}} {{claim:spec.paper.bonus-token}} {{claim:vllm.cudagraph.mrv1-query-len}}
16. **The GPU price of a step** comes from a cost card, applied to the padded batch. One card is kernelspace's S5 step card on one of its fitted rows, `70B on H100` and its siblings, vendored at d478f91 (D-031). Another, for TR2's levels, is a small model on a learner's card at S5's datasheet bound (S5's `NAPKIN`, with no fixed terms): a napkin and not a fit, whose shapes are the model's own round figures, so its numbers are synthetic and its host work is the host card's alone (W1-T13). The third is the front page's synthetic tick card (GAMES.md §3.1, D-048). The expo plans a fire in {{claim:loop.world.plan-ticks}} and the line cooks it in {{claim:loop.world.forward-ticks}}, with {{claim:loop.world.admit-ticks}} more when the fire hangs a ticket for the first time. The expo then reads the fire back in {{claim:loop.world.read-ticks}} of its own.
17. **The CPU price of a step** comes from a host card of integer µs per phase. Its values are [estimated] presets per runner until W2-T22 fits them to the owner's traces. S5 fitted a host term per running sequence, `t_seq`. The model puts it on the CPU lane by default, where async scheduling can hide it under the forward, and keeps it inside the GPU step, as S5 fitted it, when a caller asks. The default is D-044, which is proposed: the owner has not confirmed it, and every card that shows the choice says so. Hiding the term under the forward is an extrapolation beyond S5's additive fit. Either way the term replaces the host card's per-sequence schedule and sample phases, so no host work is counted on both lanes.
18. **What a run reports.** GPU busy time; bubbles, which are GPU idle time while `cpu-main` is busy (the GPU waits on the CPU), where GPU idle time while `cpu-main` is idle too is the engine waiting for a request and is not a bubble; useful, ghost and padded tokens; the mode each step ran in and the graph it hit or missed; the time of the mask fills and of the drafts; the rounds, drafts and accepted drafts of a speculative run; and TTFT and TPOT per request. TTFT counts from the request's due time, and both are read at the moment the `sample` phase updates the request (A§5.3).

## Ignores

- **S5's own list** (kernelspace `docs/specs/s5.md` §3.5, read 2026-11-04 at d478f91), which the GPU lane inherits: speculative decoding and MTP; MoE routing and EP all-to-all; CUDA-graph batch buckets; tile and wave quantisation; attention-kernel path changes (sliding window, MLA); clocks and thermals; preemption cost (the box excludes it); prefix caching (the harness ran with it off); disaggregated KV transfer; multi-node; any model, precision, engine release or token budget other than the row's.
- **CUDA-graph batch buckets, in particular.** S5's fit holds no graph padding, so the model prices a padded step by giving S5's card the padded batch. That is an extrapolation beyond the fit. The same goes for the drafts of a speculative step, which S5 does not price, and for the kernels of an adapter.
- **Host variance.** Every host phase costs the same integer µs on every step, where a real CPU's phases vary from step to step with cache state, Python garbage collection, the operating system's scheduling and other processes. A run has no jitter, so its bubbles replay exactly. Synthetic traces add seeded jitter afterwards (A§5.7).
- **Kernel-level variation within a step.** A forward is one span, whatever the kernels inside it. In particular, the sampling kernel of a step whose bitmask is still being filled is inside the forward span, so a late mask delays the CPU lane and never stretches the forward. {{claim:vllm.mask.deferred-sampling}}
- **Eager launches overlapping their own forward.** The model draws the whole launch before the forward (A§5.3). A real eager launch runs the first kernel while the second is still being launched, so on a GPU-bound step the model overstates what eager launching costs.
- **The frontend.** Tokenization, detokenization, the hop between the frontend and the engine core, HTTP and streaming. Latencies are the engine core's.
- **The KV manager (W1-T21).** There is no capacity limit, no preemption and no prefix hit, and the graph memory of the model above sizes a budget that nothing in the loop enforces.
- **Parts of the dispatchers that no configuration of the model reaches.** Dual-batch overlap (a microbatch count other than one), varlen decode graphs for adaptive verification, dynamic speculative decoding with several decode query lengths, the filters for encoder-decoder models, and data-parallel padding. The ports leave them out, and the notes in `packages/sim/steploop/graphs.ts` say where.
- **Breakable graphs and capture time.** vLLM can break a graph at a chosen op, and capturing a graph takes time at start-up. The model captures nothing at run time, every graph exists from the first step, and the start-up is not on any lane. {{claim:vllm.cudagraph.breakable-off}}
- **The scheduler's padding of a new speculative request.** With speculation the scheduler pads a request that is new to the running set and has a single token to schedule up to `1 + num_spec_tokens`, to keep the decode batch uniform, and leaves it out of the step when the budget is short. The model schedules a one-token prompt as the prefill row it is. {{claim:vllm.scheduler.spec-pad}}
- **A stop at the length cap.** The scheduler does not schedule an extra step for a request that the steps in flight are sure to bring to its `max_tokens`, so such a stop leaves no ghost token. The model treats every workload length as an EOS stop, which the engine cannot know ahead, so a benchmark that fixes the output length gets a ghost token that the real engine would not compute. {{claim:vllm.scheduler.skip-extra-step}}
- **SGLang's loop.** The model follows vLLM's engine core. SGLang's batch defaults and bucket lists are data (`engine-defaults.ts`), and its scheduler, its overlap and its mask handling are not modelled.
- **Where the mask is filled.** The model fills the bitmask on `cpu-main`, the engine core's thread, as the engine does in `EngineCore.step`, and prices a row alike on every step. The grammar compilation that precedes the first step of a structured request runs on a thread pool and is not on any lane. {{claim:vllm.mask.grammar-compile-async}}
- **The engine core's sleep when requests remain but none can run, and pipeline parallelism.** {{claim:vllm.step.idle-sleep}}

## Calibrated against

- **The GPU lane, on the S5 card:** S5's three fitted rows, inside their box, and nothing else. kernelspace adopted the fit on 2026-10-18 without the owner's signature, and its split between terms is a fit, not a hardware fact. Outside the box, a screen says "napkin" or "estimated" (WORLD §4.2).
- **The host card:** nothing yet. Its values are [estimated] until W2-T22 fits them, and every screen that shows a host µs says "estimated". The price of a bitmask row is one of them.
- **The tick card:** nothing. Its tick counts are [estimated] and synthetic, and the front page says so (D-048).
- **The small-model card:** nothing. It is S5's form at the datasheet bound on shapes of the model's own, synthetic, and TR2's levels say so.
- **The graph memory and the cost of a draft:** nothing yet. No capture has been measured on a card and no draft model has been timed, so a graph's memory and a draft's share of a decode step are [estimated], and the card's screens say so.
- **The loop's structure, the capture sizes and the dispatchers:** the pinned source, read at v0.33.0 on 2026-11-04, through the claims above. The two dispatchers are also held to a second port of the same code, written apart from them, on thousands of drawn cases. The table of the pinned code's own answers, which `scripts/tables/vllm-dispatch.py` writes, is not committed yet: the owner runs it (Q-10), and W1-T13's `keys` level waits for it.
- **Traces:** none. No trace has been compared with a run yet, because the owner has not captured any. The validation panels (WORLD §4.5) arrive with W2.
- **The model's own invariants:** goldens at fixed seeds, and properties over seeded runs that `tests/sim/steploop.test.ts` and `tests/sim/steploop-v1.test.ts` check: GPU spans never overlap, busy time stays inside the horizon, no step reads a token before it is sampled, and tokens are conserved.
