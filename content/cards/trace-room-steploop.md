The notional machine behind Service's practice run and TR2: `packages/sim/steploop`, at version v0, built as the TR2 spike (W0-T13, D-040). It runs one engine core's busy loop in integer µs on two lanes, `cpu-main` (the engine core's thread) and `gpu-stream` (the default CUDA stream). It takes a seeded workload and a configuration, and returns the lanes, a record per step and per request, and any violations. Its rules follow vLLM v0.33.0, the course's pin. The real engine is authoritative: when it disagrees with this card, the card is wrong.

## Models

1. **One step.** On `cpu-main` the step runs `schedule`, then `prepare` and `launch`. On `gpu-stream` its `forward` starts when the launch has ended and the stream is free. Back on `cpu-main`, `sync` returns the sampled ids to the host once the forward has ended, and `sample` updates the requests from them and checks for stops. vLLM's `EngineCore.step` makes the same calls in the same order. {{claim:vllm.step.order}}
2. **The scheduler.** One token budget per step, handed out to every request so that each catches up with the tokens it should have, and a cap on running requests. Running requests come first, one token each, and waiting requests follow in arrival order, which is vLLM's default policy. Chunked prefill is on, as it is by default in vLLM, so a prompt is cut into chunks to fit the budget. With it off, a prompt is admitted whole or not at all. The model emits a request's first token in the step that completes its prompt. Static batching, which the front page's first lane runs, forms a batch and admits nothing while any request of it is live in the engine's view (GAMES.md §3.1, D-043). {{claim:vllm.scheduler.no-phases}} {{claim:vllm.scheduler.order}} {{claim:vllm.scheduler.policy-default}} {{claim:vllm.scheduler.chunked-prefill-default}}
3. **Where a request ends.** A request's output length is the truth about it, and the scheduler never reads it. The request stops on EOS, and the engine learns of it only when the step that carries its last token is read back. On the front page the visitor hangs requests by hand, and a request's length is settled when it is hung: the k-th request hung gets the k-th length of the seed's workload, whatever its number, so the order the visitor taps in cannot change a run (GAMES.md §3, WORLD §2.2). {{claim:vllm.scheduler.stop-check}}
4. **Async scheduling off** is strictly serial (WORLD §2.6): the next step's `schedule` starts only after this step's `sample`.
5. **Async scheduling on** is the default in vLLM, and has been since v0.14.0. Up to two steps are in flight, as the engine's batch queue allows at one pipeline stage. The next step is scheduled, prepared and launched before the oldest step's result is waited for, so that CPU work overlaps the forward in flight. A request that stops on EOS still rides the next step, because the engine has not read the stop yet, and that step's token for it is thrown away: a ghost token (WORLD §2.6). {{claim:vllm.async-scheduling.default}} {{claim:vllm.async-scheduling.since}} {{claim:vllm.step.max-concurrent-batches.mrv2}} {{claim:vllm.mrv2.async-first}}
6. **The dependency check** (A§5.3). With async scheduling the previous step is still in flight when the next one is prepared. If the input ids are written on the device, as MRV2's GPU-side input preparation does, the stream's order makes each token ready before the forward reads it. If the CPU writes them from the host, it reads tokens that are not sampled yet, and the step raises a violation. Graded levels count violations (ASSESSMENT §4.3). {{claim:vllm.mrv2.gpu-input-prep}}
7. **CUDA graphs, full replay only.** With graphs on, a step's token count is padded up to the smallest captured size at least that large. Unless the user lists sizes, vLLM captures a default list. {{claim:vllm.cudagraph.capture-sizes}} Its largest size is capped by default at {{claim:vllm.cudagraph.max-capture-size}}, or at {{claim:vllm.cudagraph.max-capture-size-blackwell}} on data-centre Blackwell. On a hit, which is any step whose padded token count was captured, whether it only decodes or mixes in a prefill chunk, the launch costs one graph replay and the padded tokens are computed and wasted. Above the largest captured size, or with graphs off, the step launches one kernel at a time: kernels per layer, times layers, times the launch cost. vLLM has five graph modes. NONE and FULL are modelled here, and the other three arrive with W1-T12. {{claim:vllm.cudagraph.modes}}
8. **The GPU price of a step** comes from a cost card, applied to the padded batch. One card is kernelspace's S5 step card on one of its fitted rows, `70B on H100` and its siblings, vendored at d478f91 (D-031). The other is the front page's synthetic tick card (GAMES.md §3.1, D-048). The expo plans a fire in {{claim:loop.world.plan-ticks}} and the line cooks it in {{claim:loop.world.forward-ticks}}, with {{claim:loop.world.admit-ticks}} more when the fire hangs a ticket for the first time. The expo then reads the fire back in {{claim:loop.world.read-ticks}} of its own.
9. **The CPU price of a step** comes from a host card of integer µs per phase. Its values are [estimated] presets per runner until W2-T22 fits them to the owner's traces. S5 fitted a host term per running sequence, `t_seq`. The model keeps it either inside the GPU step, as S5 fitted it, or on the CPU lane (D-044, proposed), where async scheduling can hide it. Hiding it under the forward is an extrapolation beyond S5's additive fit. Either way the term replaces the host card's per-sequence schedule and sample phases, so no host work is counted twice.
10. **What a run reports.** GPU busy time; bubbles, which are GPU idle time while `cpu-main` is busy (the GPU waits on the CPU), where GPU idle time while `cpu-main` is idle too is the engine waiting for a request and is not a bubble; useful, ghost and padded tokens; and TTFT and TPOT per request. TTFT counts from the request's due time, and both are read at the moment the `sample` phase updates the request (A§5.3).

## Ignores

- **S5's own list** (kernelspace `docs/specs/s5.md` §3.5, read 2026-11-04 at d478f91), which the GPU lane inherits: speculative decoding and MTP; MoE routing and EP all-to-all; CUDA-graph batch buckets; tile and wave quantisation; attention-kernel path changes (sliding window, MLA); clocks and thermals; preemption cost (the box excludes it); prefix caching (the harness ran with it off); disaggregated KV transfer; multi-node; any model, precision, engine release or token budget other than the row's.
- **CUDA-graph batch buckets, in particular.** S5's fit holds no graph padding, so the model prices a padded step by giving S5's card the padded batch. That is an extrapolation beyond the fit.
- **Host variance.** Every host phase costs the same integer µs on every step, where a real CPU's phases vary from step to step with cache state, Python garbage collection, the operating system's scheduling and other processes. A run has no jitter, so its bubbles replay exactly. Synthetic traces add seeded jitter afterwards (A§5.7).
- **Kernel-level variation within a step.** A forward is one span, whatever the kernels inside it.
- **Eager launches overlapping their own forward.** The model draws the whole launch before the forward (A§5.3). A real eager launch runs the first kernel while the second is still being launched, so on a GPU-bound step the model overstates what eager launching costs.
- **The frontend.** Tokenization, detokenization, the hop between the frontend and the engine core, HTTP and streaming. Latencies are the engine core's.
- **Not in v0.** Unless a task is named, W1-T12 builds it:
  - the KV manager (W1-T21), so there is no capacity limit, no preemption and no prefix hit;
  - the PIECEWISE, FULL_DECODE_ONLY and FULL_AND_PIECEWISE graph modes, the dispatch keys, and graph memory;
  - the structured-output mask, speculation and adapters;
  - the runner presets' effect beyond the host card, and the per-GPU engine defaults;
  - the engine core's sleep when requests remain but none can run, and pipeline parallelism. {{claim:vllm.step.idle-sleep}}

## Calibrated against

- **The GPU lane, on the S5 card:** S5's three fitted rows, inside their box, and nothing else. kernelspace adopted the fit on 2026-10-18 without the owner's signature, and its split between terms is a fit, not a hardware fact. Outside the box, a screen says "napkin" or "estimated" (WORLD §4.2).
- **The host card:** nothing yet. Its values are [estimated] until W2-T22 fits them, and every screen that shows a host µs says "estimated".
- **The tick card:** nothing. Its tick counts are [estimated] and synthetic, and the front page says so (D-048).
- **The loop's structure and the default capture sizes:** the pinned source, read at v0.33.0 on 2026-11-04, through the claims above. No trace has been compared with a run yet, because the owner has not captured any. The validation panels (WORLD §4.5) arrive with W2.
- **The model's own invariants:** a golden run at the practice seed, and properties over seeded runs that `tests/sim/steploop.test.ts` checks: GPU spans never overlap, busy time stays inside the horizon, and tokens are conserved.
