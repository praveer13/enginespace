The notional machine behind The Reach-In (`pool`) and the `hybrid-kv` forge lab: `packages/sim/kv`, built by W1-T21. It manages one pool of physical pages for several KV groups and, in the learner's design, for adapters too. Its rules follow vLLM v0.33.0 and SGLang v0.5.23, and the adapter pages are the learner's design and not the engines' own mechanism (D-042). The real engine is authoritative: when it disagrees with this card, the card is wrong.

## Models

1. **One pool, one page size.** One physical page pool serves every group and every adapter, and every block is exactly one page (D-045, A§5.4). vLLM's hybrid manager does the same for its layer types, and making them all reach one page size is its core challenge. The size of the pool is an input, the number of pages the spec says. {{claim:vllm.hybrid-kv.single-pool}}
2. **Grouping the layers.** A preset reaches the page size as the planner at the pin does. Layers of one kind share a block table, and every group has the same number of layers, which is the fewest that any kind has, or the most when that is less than a given multiple of the fewest. A kind that does not divide evenly spreads its layers over its groups, and the missing layers are padding that the preset reports as waste. For a model with recurrent layers the attention block grows until it holds a layer's state, and the state is padded up to it. The design document draws the padding in the last group, and the code spreads it, so the presets follow the code. {{claim:vllm.hybrid-kv.group-size}} {{claim:vllm.hybrid-kv.group-size-near}} {{claim:vllm.hybrid-kv.layer-spread}} {{claim:vllm.hybrid-kv.padding-layers}} {{claim:vllm.hybrid-kv.page-unify}} {{claim:vllm.hybrid-kv.attn-block-inflate}}
3. **Groups.** A full-attention group keeps every block. A sliding group lets go of a block once every token in it is before the window the next token reads. A state group keeps its newest few blocks however long the request runs: the block that is full holds the state at its edge, and the newest holds the live state. The pool caches a block under its hash and its group, so the same tokens in different groups are cached and evicted independently. {{claim:vllm.hybrid-kv.cache-key}} {{claim:vllm.hybrid-kv.sliding-skipped-tokens}} {{claim:vllm.hybrid-kv.mamba-align-only}}
4. **Prefix hashing.** A block's hash chains its parent's hash, its token ids and its extra keys. An adapter's identity is one of the extra keys, so two requests share a block only when they use the same adapter. The model's hash is its own, a number of 53 bits [derived] that an integer-only program computes the same way everywhere, where the engine defaults to SHA-256. {{claim:vllm.kv-hash.chain}} {{claim:vllm.kv-hash.sha256-default}} {{claim:vllm.kv-hash.lora-extra-key}}
5. **The N-group hit.** A request's cache hit is the longest prefix that every group holds, which is the intersection of the groups' hits. The lookup is an iterative fixed-point search over all the groups, full attention first, and the hit is a multiple of the least common multiple of the groups' block sizes. It never covers the last token of the prompt. A full group needs every block from the start, a sliding group the blocks its window reads before the edge or all it has when there are fewer, and a state group the one block that holds the state at the edge. The design document still says the coordinator handles exactly two groups, and the model follows the code. {{claim:vllm.hybrid-kv.intersection}} {{claim:vllm.hybrid-kv.n-group-lookup}} {{claim:vllm.hybrid-kv.doc-two-groups}} {{claim:vllm.hybrid-kv.full-attention-first}} {{claim:vllm.hybrid-kv.hit-alignment}} {{claim:vllm.hybrid-kv.scheduler-block-size}} {{claim:vllm.kv-pool.max-hit-length}} {{claim:vllm.hybrid-kv.sliding-hit-blocks}} {{claim:vllm.hybrid-kv.sliding-hit-prefix}} {{claim:vllm.hybrid-kv.mamba-hit}}
6. **Eviction.** One queue of free blocks, in eviction order, serves every group. An allocation takes from the front, and a cached block that it takes loses its hash. A block that nobody holds any more joins the queue, at the back when it has a hash, so that cached blocks leave oldest first, and at the front when it has none, so that it is reused before any cached block is touched. A request's blocks go back last block first, so the tail of a prefix is evicted before its head. A hit takes the blocks it uses out of the queue, and the ones it read and does not keep go back to the back. {{claim:vllm.hybrid-kv.one-lru}} {{claim:vllm.kv-pool.allocate-from-front}} {{claim:vllm.kv-pool.free-order}} {{claim:vllm.kv-pool.free-reverse}} {{claim:vllm.kv-pool.touch}}
7. **All or nothing.** An operation either succeeds or leaves the state untouched, the rule of kernelspace's `lab 02` (A§5.4). A request fits when its new blocks fit once the cached blocks of its hit have left the queue. vLLM frees the blocks a window has left behind before it checks, and keeps them freed when the request does not fit, which the model does not do. {{claim:vllm.kv-pool.admission-counts-evictable}} {{claim:vllm.kv-pool.skipped-freed-first}}
8. **Preemption** is by recompute only: the victim's blocks are freed, its computed tokens go back to zero and it returns to the front of the waiting queue. In the model that is a finish, and the freed blocks stay cached until they are evicted. {{claim:vllm.scheduler.preemption-recompute}}
9. **Capacity** is the memory budget, less the weights, the activation workspace and the CUDA-graph reservation, divided by the bytes in a page (WORLD §2.4). vLLM estimates the graph memory before it allocates the KV cache and takes it off what the cache may use, and has done by default since v0.21.0. A block holds {{claim:vllm.cache.block-size-default}} by default in vLLM, and prefix caching is on by default. The model takes the resulting number of pages as given. {{claim:vllm.cudagraph.memory-before-kv}} {{claim:vllm.cudagraph.memory-subtracted}} {{claim:vllm.cudagraph.memory-profiling-default-since}} {{claim:vllm.cache.prefix-caching-default}}
10. **Adapters, two policies.** The learner's design is S-LoRA's unified paging: an adapter takes ⌈adapter bytes ÷ page bytes⌉ pages of the same pool, stored non-contiguously, shared by every request that uses the adapter and admitted all or nothing (D-042, D-045). The baseline it is compared with is what both engines ship at the pins, a fixed number of slots outside the KV pool, which a spec asks for with `adapterSlots`. vLLM sizes its slots by `max_loras` and admits a request only while the distinct adapters of its batch stay within them. SGLang's pool is a fixed table of slots, which it fills and evicts by policy. {{claim:kv.slora.unified-paging}} {{claim:vllm.lora.slot-count}} {{claim:vllm.lora.admission-cap}} {{claim:sglang.lora.pool}} {{claim:sglang.lora.slot-search}}
11. **Events.** The model emits `BlockStored`, `BlockRemoved` and `AllBlocksCleared` in `kv-events@1` (D-034), in the shape of vLLM's events, which travel in batches. A stored block carries its adapter, as SGLang's does, so a consumer can rebuild the cache per adapter, and the kind and window of its group. One event covers the blocks that one operation cached in a group, a removal is one event for each evicted hash in the order the pages are taken, and a reset is one event and no removals. vLLM does not de-duplicate cached blocks, so it can hold two copies of one block and publish both, and the model caches the first and publishes it once. {{claim:vllm.kv-events.batch}} {{claim:vllm.kv-events.stored-content}} {{claim:vllm.kv-events.block-removed-emission}} {{claim:vllm.kv-events.all-blocks-cleared}} {{claim:vllm.kv-events.extra-keys}} {{claim:vllm.kv-events.spec-kind}} {{claim:vllm.kv-events.spec-annotation}} {{claim:vllm.kv-events.adapter-field}} {{claim:sglang.kv-events.adapter-field}} {{claim:vllm.kv-pool.duplicate-keys}} {{claim:vllm.kv-events.duplicates-published}}
12. **Invariants.** Pages are conserved, reference counts never go below zero, a block table's length follows its group's rule, the cache is the pages that hold hashes, the queue is the pages that can be allocated, and every stored or removed block is published exactly once (A§5.4).

## Ignores

- **The physical layout of bytes within a page.** A page is a unit of accounting, and the model does not say how a key or a value sits inside it.
- **Kernel efficiency per page size.** A page size changes how fast attention runs on a real GPU. The model counts pages and nothing else about them.
- **Copy-on-write costs.** Sharing a block is free in the model, and a real copy of a shared block is not. A hit never ends inside a block, so the model never shares a block that a request goes on to write.
- **Chunked prefill.** An admit computes the whole prompt in one operation, and a sliding group takes only the blocks inside its window at the end of the prompt. vLLM allocates chunk by chunk and caps what a sliding group reserves for a request, and it caches the blocks that a window passes while a long prompt is prefilled. The model never caches a block that the window had already left when the prompt ended.
- **When blocks are freed.** vLLM frees a window's blocks on the processed-token count, a step behind the model, which frees them as soon as the tokens that leave the window are stored.
- **Other kinds of group.** Chunked local attention, cross attention, circular buffers, sink attention, reference sliding windows (R-SWA) and the HiSparse managers are in vLLM's code and not in the model. Neither are speculative blocks, EAGLE's last-block drop, hashes finer than a block, and the parallelism that shards a block across ranks.
- **The Mamba modes other than align.** The model's state group is the align mode's: a state is cached at each block edge that a request leaves behind it, and a hit reads one. It does not model the sparse retention of edges or a state's copy from one block to the next.
- **CPU swap and every tier beyond the GPU.** TR5b's `tiers` model owns the tiers, the connector and its events (A§5.8).
- **Adapter compute.** An adapter is a number of pages that must be resident. The model says nothing about the cost of the LoRA kernels that use it.
- **The bytes of a real model.** The presets' layer counts and the window of the first example come from vLLM's design document, and every byte count and the other windows are the model's own and synthetic [estimated].

## Calibrated against

- **Nothing numeric.** The model's rules are claims from the pins, read at v0.33.0 and v0.5.23 on 2026-11-04, and no engine run has been compared with the model's counts yet.
- **vLLM's own prefix-hit search,** ported from the pinned source into the tests and compared with the model's on thousands of random specs, prompts and caches, and with a brute-force statement of the rule.
- **A second manager,** written for the tests from the same rules in a different way, which agrees with the model on every reply, event and state over seeded streams of every preset and of specs the presets do not reach.
- **The model's own invariants,** which the tests check after every operation of seeded streams, and the known-wrong managers of its bestiary, each of which must fail a named check (A§5.10).
