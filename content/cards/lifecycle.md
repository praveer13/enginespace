The notional machine behind Back of House (`engine-floor`) and TR1's span checks: `packages/sim/lifecycle`, built by W1-T16. It draws one request's path through an engine's processes as data, and the order of the stages is the model. The engines are vLLM v0.33.0, the vLLM commit that the post "Inside vLLM" reads, SGLang v0.5.23, and the two small engines the course reads, Mini-SGLang at `9a91cfa` and nano-vllm at `bb823b3`. Every stage cites its file, its symbol, a line and a quote of that line at the commit its engine is pinned to, and a test checks each citation against the unpacked source of the pin when it is given that source. The real engine is authoritative: when it disagrees with this card, the card is wrong.

## Models

1. **A path is a list of stages.** Each stage has a location, which is a process, a thread and a device, and a mechanism, which is a call, a queue, IPC, shared memory, a copy, a launch, a collective or a sync (A§5.8, GAMES.md §5). A stage starts where the one before it ended, and its mechanism is the way it crosses the boundary between its two places: a queue between threads, IPC or shared memory between processes, a copy or a launch between the host and a GPU, a collective between the GPUs of two ranks. A copy to the host leaves the value not yet there, so no stage reads it before a sync, and only a queue may carry it meanwhile.
2. **The model follows the request's data.** A host call that only starts GPU work is not a stage, and the stage is the GPU running what was launched. A path is one lap of the engine's loop for one request, from the client's call to the first token that comes back, and the loop's repetition for the next token is not drawn (GAMES.md §5).
3. **vLLM** runs the API server and the engine core as two processes joined by ZMQ. The engine core has an input thread, a busy loop and an output thread, joined by `input_queue` and `output_queue`, and the busy loop schedules, launches the forward, waits, and updates the scheduler. With async scheduling, the default, it keeps the launched batches in `batch_queue`, and Model Runner V2 copies the sampled ids on a stream of its own and waits on an event. {{claim:vllm.request.engine-core-process}} {{claim:vllm.engine-core.queues}} {{claim:vllm.engine-core.busy-loop}} {{claim:vllm.step.batch-queue}} {{claim:vllm.async-output.copy-stream}} {{claim:vllm.async-output.event-sync}}
4. **A vLLM request is always in a state.** The model keeps the names of the pinned version, and not those of the Inside vLLM post, which reads an older commit than the pin. The HTTP entry that the post names has moved too. {{claim:vllm.request.states}} {{claim:inside-vllm.analysis-commit}} {{claim:vllm.http.api-server-shim}}
5. **SGLang** has three components: the tokenizer manager, which runs in the main process, the scheduler in a subprocess, and the detokenizer manager in another subprocess. They are joined by IPC over ZMQ. The scheduler's loop launches one batch and then processes the result of the batch before it, so the CPU work on a result overlaps the next batch's GPU work. {{claim:sglang.engine.components}} {{claim:sglang.engine.ipc}} {{claim:sglang.overlap.loop}}
6. **Mini-SGLang** is the small answer key: several independent processes, which are the API server, a tokenizer worker, a detokenizer worker and one scheduler worker for each GPU. They use ZeroMQ for control messages and NCCL for the tensors that the GPUs exchange. Its documented request path is a short run of hand-offs from the API server through the tokenizer, the schedulers and the detokenizer, and back, and its scheduler overlaps by default. {{claim:mini-sglang.processes}} {{claim:mini-sglang.transport}} {{claim:mini-sglang.request-path}} {{claim:mini-sglang.overlap-default}}
7. **nano-vllm** has one scheduler that picks prefill or decode for each step, so a step is all prefill or all decode. It is offline: the caller, the scheduler and `rank 0` share one process and one thread, so at one rank the path crosses no process and no thread. Only `rank 0` samples, and it copies the ids to the host with `.tolist()`, which PyTorch makes a wait for the GPU as well, so the model draws that line as a copy and then a sync. {{claim:nano-vllm.step-shape}} {{claim:nano-vllm.rank0-samples}} {{claim:lifecycle.torch.copy-synchronizes}}
8. **Two ranks.** The model follows the request through `rank 1` and back to `rank 0`, which samples and sends the result on, and `rank 0`'s own copies and launches, which run beside `rank 1`'s, are not drawn. nano-vllm starts a worker process for `rank 1` and joins it by shared memory and an Event, and the LM head gathers the logits to `rank 0`. vLLM's executor enqueues each step on a shared-memory queue, and the workers answer on one. SGLang's and Mini-SGLang's schedulers at `rank 0` broadcast each request to the other ranks. {{claim:nano-vllm.tp-worker-process}} {{claim:nano-vllm.tp-shared-memory}} {{claim:nano-vllm.logits-gather}} {{claim:vllm.executor.rpc-broadcast}} {{claim:vllm.executor.message-queue-shm}} {{claim:sglang.tp.request-broadcast}}
9. **A prefix hit and `n`.** A prefix hit adds the stage where the engine finds the shared blocks or radix node and takes a reference on them (GAMES.md §5). A request for two samples adds a fan-out in vLLM, where the API server's client makes a child request for each. SGLang instead sends the shared prompt first with `max_new_tokens` set to zero, to cache its prefix, and then the samples. Mini-SGLang reads no `n`, and nano-vllm has none, so each supports one sample. {{claim:sglang.parallel-sampling.warmup}} {{claim:mini-sglang.n-ignored}}
10. **An abort** is a client that leaves mid-stream, so it needs streaming, and its path follows the first streamed token. In the pinned vLLM it reaches the engine core on a queue of its own, which the step drains after the forward returns and before it updates the scheduler, and the request then ends in FINISHED_ABORTED. At the commit the post reads, it waits in the input queue behind the step in flight. In SGLang the scheduler marks the running request to finish, and in Mini-SGLang the API server tells the tokenizer, which tells the scheduler. {{claim:vllm.engine-core.aborts}} {{claim:vllm.engine-core.abort-status}} {{claim:inside-vllm.abort-input-queue}} {{claim:sglang.abort.running-request}}
11. **A synthetic trace** is a scenario's path written as `trace@1`: one span for each stage, named by the stage's id, on the track of the thread or the stream where it works, with a CUDA API span before each piece of GPU work and one step window around the lap. It passes `traceChecks`, and a sync span ends after the GPU work it waits for (A§5.7, A§5.8, ASSESSMENT §5.9).

## Ignores

- **Durations.** The model keeps the order of the stages and says nothing about how long a stage takes. A synthetic lifecycle trace has to give its spans times, and those times are made up and labelled synthetic (A§5.7, A§5.8).
- **Batching with other requests.** The path is one request's, as if it ran alone.
- **The loop's repetition.** A request needs a step for each token, and the path draws one lap of them.
- **Failure modes other than abort.** An error, a length cap and a stop on repetition are states of a request (the states above), and the model draws none of their paths.
- **Small things that sit between two stages.** The several small copies of one step are one copy. The host calls that only launch GPU work, the tokenizer's thread pool, logging and metrics, and the second RPC of a two-rank vLLM step, which carries no request, are not stages. SGLang's relay of the last tokens on the GPU, which matters from a request's second step on, and its CPU-side copy worker, which runs under confidential computing only, are not drawn either.
- **The file names of the reading targets.** The stages are graded by their mechanism and their location, because a file name moves between releases, and the HTTP entry that the Inside vLLM post names already has. {{claim:vllm.http.api-server-shim}}

## Calibrated against

- **The pinned source, stage by stage:** W1-T16 checked each stage against its file at its commit on 2026-11-04. The check compares a quote and a line, and the definition around the line, with the unpacked tarball of the pin, and it runs again at each re-pin (`tests/sim/lifecycle-sources.test.ts`).
- **A lifecycle trace of each engine family:** nothing yet. The owner's first captures arrive with W2-T21, and until then every trace the site shows of a lifecycle is synthetic.
- **The durations of the synthetic trace:** nothing. A nominal for each mechanism and a seeded spread are judgments [estimated].
